# qwdtt-cli

Консольный клиент к протоколу qWDTT: VPN поверх TURN-инфраструктуры звонков VK.
Трафик уходит на ваш VPS через TURN-relay ВКонтакте и для сети выглядит как медиапоток
звонка WebRTC, а не как подключение к VPN-серверу.

Это только клиент. Установка и настройка серверной части, панель управления, импорт
подписок и сканирование QR остаются в Android-приложении
[qWDTT](https://github.com/SpaceNeuroX/proxy-turn-vk-android) — здесь их нет и не будет.
Чтобы подключиться, у вас уже должны быть адрес сервера, пароль подключения и хотя бы
один хеш звонка VK — те же, что вводятся в приложении.

Клиент работает на переднем плане: пока запущен `tt connect`, туннель поднят.
Службы и автозапуска нет. Первый Ctrl+C останавливает туннель и убирает за собой,
второй убивает процесс.

## Установка

Готовая сборка — архив `tt_<версия>_windows_amd64.zip`: распакуйте в любой каталог.
В нём `tt.exe`, `wintun.dll` с её лицензией `wintun-LICENSE.txt`, пример настроек
`tt.example.toml`, лицензия, лицензии сторонних компонентов `THIRD_PARTY_NOTICES.txt`
и этот файл. Установка не нужна, права администратора для режима по умолчанию — тоже.
Они нужны режиму `tun`, который пускает через туннель весь трафик системы;
`wintun.dll` для него уже лежит в архиве и должна оставаться рядом с `tt.exe`.

### Сборка под Windows

Нужен Go 1.26 или новее, cgo не требуется. Из корня репозитория:

```
go build -o build\out\tt.exe ./cmd/tt
```

Этого достаточно для режимов `socks` и `external`. Режиму `tun` (свой сетевой
адаптер, нужны права администратора) нужна ещё `wintun.dll` — библиотека драйвера
Wintun от авторов WireGuard. В репозитории её нет: это чужой бинарь под своей
лицензией. Скачать и проверить её можно скриптом, он кладёт DLL в `build\out`
рядом с `tt.exe`:

```
pwsh scripts/fetch-wintun.ps1
```

Скрипт берёт фиксированную версию Wintun (сейчас 0.14.1) с wintun.net, сверяет
SHA256 архива с зашитым в скрипт, проверяет подпись DLL (WireGuard LLC) и копирует
`wintun.dll` вместе с её лицензией. Хеш не совпал или подпись не та — скрипт
останавливается и ничего не копирует. Другая архитектура — `-Arch arm64`, другой
каталог — `-Dest <путь>`, без сети — `-Archive <путь к wintun-0.14.1.zip>`.

Можно и вручную: скачайте `wintun-0.14.1.zip` с https://www.wintun.net, сверьте хеш

```
(Get-FileHash wintun-0.14.1.zip).Hash
07C256185D6EE3652E09FA55C0B673E2624B565E02C4B9091C79CA7D2F24EF51
```

и положите `wintun\bin\amd64\wintun.dll` рядом с `tt.exe`. DLL ищется только
в каталоге `tt.exe` и в System32 — текущий каталог консоли и `PATH` не подходят.
Без неё `tt connect -datapath tun` откажет сразу, до подключения:
«рядом с tt нет файла wintun.dll».

### Сборка и отладка под Linux

Сборка та же, Go 1.26 или новее, cgo не нужен:

```
go build -o build/out/tt ./cmd/tt
```

На Linux пока работает только режим `socks`, и ему ничего, кроме самого `tt`,
не нужно: ни прав root, ни системных пакетов. Режимы `external` и `tun`
здесь пока не поддерживаются.

Для отладки и для будущего режима со своим адаптером на Linux пригодятся
пакеты (имена — для Debian и Ubuntu):

```
sudo apt install wireguard wireguard-tools iproute2 nftables tcpdump resolvconf
```

- `wireguard`, `wireguard-tools` — модуль ядра и `wg`, `wg-quick`: сверить конфиг
  от сервера и поднять туннель вручную. Сам `tt` wireguard-go встраивает
  библиотекой, отдельный `wireguard-go` не нужен.
- `iproute2`, `nftables` — `ip route`, `ip rule`, `ss`, `nft`: маршруты и правила
  при поднятом туннеле.
- `tcpdump` — убедиться, что трафик и DNS идут через туннель, а не мимо.
- `resolvconf` — без него `wg-quick up` падает на конфиге со строкой `DNS =`.

> Если сетью управляет NetworkManager, после установки `resolvconf` файл
> `/etc/resolv.conf` становится ссылкой на `/run/resolvconf/resolv.conf` и
> до перезапуска NetworkManager остаётся без серверов — DNS на машине не
> работает. Чинится `sudo systemctl restart NetworkManager`.

### Релиз

Релиз для трёх платформ собирает `pwsh scripts/build-release.ps1`; `wintun.dll`
в zip для Windows он кладёт тем же `fetch-wintun.ps1` (без сети — с
`-WintunArchive <путь>`), а `THIRD_PARTY_NOTICES.txt` собирает
`go run ./scripts/notices` — лицензии всех модулей, слинкованных в `tt.exe`,
и самого Go. Модуль без файла лицензии или с нераспознанной лицензией
останавливает сборку: новую зависимость надо разобрать вручную. Бинари для Linux
и macOS собираются и запускаются; режимы `external` и `tun` там пока не
поддерживаются. На Linux режим `socks` проверен вживую, на macOS — ещё нет.

## Быстрый старт

1. Заведите профиль. Пароль и хеши спрашиваются скрытым вводом; в файл настроек
   попадают только ссылки на хранилище секретов (на Windows — DPAPI, привязка к вашей
   учётной записи):

   ```
   tt profile set home -peer example.org:56000
   ```

2. Проверьте хеши и задержку до сервера. Обе команды не поднимают туннель:

   ```
   tt hashes
   tt ping
   ```

   `hashes` печатает по строке на хеш со статусом `ok`, `captcha`, `dead`, `limited`,
   `network` или `error` и возвращает код 1, если годных нет.

3. Поднимите туннель:

   ```
   tt connect
   ```

   Через секунду-две в выводе появится `[SOCKS] слушает 127.0.0.1:1080` и
   `== туннель работает`. Направьте на этот адрес браузер или приложение, которое
   умеет ходить через прокси SOCKS5. Проверить можно так:

   ```
   curl -x socks5h://127.0.0.1:1080 https://example.org/
   ```

   Имя профиля можно опускать, если профиль один или назван в `default_profile`.
   Флаг перекрывает то же поле профиля на один запуск: `tt connect home -workers 27`.
   `-v` печатает весь лог ядра. На терминале внизу держится статусная строка
   с состоянием, аптаймом и счётчиками; при перенаправлении в файл её нет.

4. Чтобы через туннель шёл весь трафик системы, а не только программы с прокси,
   запустите на Windows из консоли от имени администратора

   ```
   tt connect -datapath tun
   ```

   или запишите `datapath = "tun"` в профиль. Подробности — в разделе
   «Режимы доставки трафика».

Если VK попросит капчу, которую ядро не осилило само, на Windows откроется окно
со страницей капчи: решите её, и окно закроется само, а `tt` продолжит. Срок
написан в заголовке окна. Если окна не видно, оно может оказаться за консолью —
поищите его на панели задач. Окну нужен WebView2 Runtime: он есть в Windows 11 и в актуальных
Windows 10. Если Runtime нет, если `tt` запущен по SSH или система не Windows,
в stderr вместо окна появится ссылка и инструкция: открыть её в браузере, решить,
вставить токен. На это даётся три минуты.

## Файл настроек

`profiles.toml` лежит в каталоге настроек пользователя: на Windows это
`%APPDATA%\qwdtt-cli\`, рядом — `secrets.json` с зашифрованными секретами.
На Linux и macOS — `$XDG_CONFIG_HOME/qwdtt-cli/` (обычно `~/.config`), секреты
там не шифруются и защищены правами `0600` на файл.
Другой путь — флаг `-config`. Файл правится командой `tt profile set` или руками,
пример со всеми полями и пояснениями — [`tt.example.toml`](tt.example.toml).

| Поле | Что задаёт | По умолчанию |
|---|---|---|
| `peer` | адрес сервера `host:port` | обязательно |
| `password_ref`, `vk_hashes_ref` | ссылки на секреты, пишет `tt profile set` | обязательно |
| `workers` | число воркеров, кратно девяти, потолок 108 | 9 |
| `obfs` | RTP-маскировка: `audio` или `video` | `audio` |
| `turn_transport` | `udp` или `tcp`; TCP помогает там, где душат UDP | `udp` |
| `dtls` | DTLS поверх TURN; `false` требует сервера с `-listen-direct` | `true` |
| `dns` | резолвер для доменов VK: `yandex`, `cloudflare`, `google`, `doh-*`, `custom:IP`, `doh:URL` | `yandex` |
| `datapath` | как отдавать трафик: `socks`, `tun` или `external` | `socks` |
| `[profile.<имя>.socks] listen` | адрес локального SOCKS5 | `127.0.0.1:1080` |

Секреты просматриваются только замаскированными (`tt profile show`), удаляются
вместе с профилем (`tt profile rm`) и перезаписываются по `tt profile set <имя>
-password` или `-hashes`. Аргументом командной строки их передать нельзя намеренно.

## Режимы доставки трафика

Режим задаёт поле `datapath` профиля или флаг `-datapath`. Прежнее имя режима `tun` —
`wintun` — тоже принимается: старые профили и команды работают как раньше.

| Режим | Что идёт через туннель | Права | Что нужно | Системы |
|---|---|---|---|---|
| `socks` | программы, настроенные на прокси SOCKS5 | не нужны | ничего | Windows, Linux, macOS |
| `tun` | весь трафик системы | администратор | `wintun.dll` рядом с `tt.exe` | Windows |
| `external` | весь трафик системы | администратор | установленный WireGuard для Windows | Windows |

### `socks`

Режим по умолчанию: WireGuard целиком внутри процесса и локальный SOCKS5 над ним.
Прав администратора не нужно, устанавливать ничего не нужно. Ограничения: только TCP,
только IPv4, только приложения, которые умеют ходить через прокси; DNS-запросы
приложения уйдут мимо туннеля, если оно не проксирует их само (в `curl` для этого
`socks5h`, в браузерах — настройка «DNS через прокси»).

### `tun` — весь трафик системы

Основной режим полного туннеля. `tt` создаёт свой сетевой адаптер `tt` на драйвере
Wintun от авторов WireGuard, а сам WireGuard работает внутри процесса `tt`: ставить
ничего не нужно. Консоль нужна от имени администратора — адаптер, маршруты и фильтры
без прав не создать. Без прав `tt` откажет сразу, до подключения, и предложит
`-datapath socks`; без `wintun.dll` рядом с `tt.exe` — «рядом с tt нет файла
wintun.dll» (как её получить при сборке из исходников — в разделе «Сборка под
Windows»).

Пока туннель поднят:

- адаптер `tt` получает адрес и DNS-серверы, которые выдал сервер; если DNS сервер
  не прислал — `1.1.1.1`;
- весь трафик забирают маршруты `0.0.0.0/1` и `128.0.0.0/1` через `tt` (для IPv6 —
  `::/1` и `8000::/1`). Маршрут по умолчанию остаётся на месте: половины выигрывают
  у него длиной префикса;
- собственные соединения `tt` — с VK, с DNS для доменов VK и с TURN-relay — привязаны
  к физическому адаптеру и идут мимо туннеля, иначе туннель зависел бы от самого
  себя. Какой адаптер выбран, `tt` пишет строкой `netguard: …`; с `-v` видно каждое
  такое соединение строкой `[NETGUARD] … → интерфейс N`;
- DNS-запросы системы идут только к DNS-серверам туннеля (раздел «Защита DNS»).

Маршруты всегда забирают всё адресное пространство, что бы сервер ни выдал
в `AllowedIPs`. Если сервер разрешил не всё, трафик к остальным адресам уходит
в туннель и там отбрасывается, а не идёт тихо мимо него; об этом предупреждает
строка `[TUN] Внимание: сервер разрешил в туннеле не весь IPv4 (AllowedIPs: …)`.

Адаптер живёт, пока работает `tt connect`: переподключения его не пересоздают, и
Windows не заводит «Сеть 2», «Сеть 3». Второй `tt connect -datapath tun` на той
же машине откажет сразу: «адаптер уже занят: на этой машине работает другой tt
с datapath tun».

### `external`

Конфиг от сервера передаётся штатному WireGuard для Windows:
`wireguard.exe /installtunnelservice` ставит службу туннеля, при остановке она
снимается. Нужны установленный [WireGuard](https://www.wireguard.com/install/) и
консоль от имени администратора. Пока туннель поднят, служба видна в
`services.msc` как «WireGuard Tunnel: tt», а её конфиг с приватным ключом лежит в
`%APPDATA%\qwdtt-cli\tt.conf`: служба читает его при запуске. При остановке `tt`
снимает службу и удаляет файл.

Собственные соединения `tt` идут мимо туннеля, как и в `tun`. Маршрут по умолчанию
из конфига сервера (`AllowedIPs = 0.0.0.0/0`, `::/0`) `tt` записывает в `tt.conf`
двумя половинами (`0.0.0.0/1, 128.0.0.0/1`): охват тот же, но с `/0` штатный
WireGuard включил бы свой kill-switch и отрезал бы соединения `tt`. Цена — этого
kill-switch больше нет: пока туннель переподключается, трафик идёт мимо него
(раздел «Окно при переподключении»), а DNS защищает сам `tt`, как в `tun`.
Если сервер выдал маршрут только для IPv4, `tt` дописывает и половины IPv6 —
раздел «IPv6».

Если нет причин держаться за штатный WireGuard, берите `tun`: он не ставит
службу и не пишет на диск файл с приватным ключом.

### IPv6

Если сервер выдал адрес только IPv4, IPv6 машины не идёт мимо туннеля с вашим
настоящим адресом, а блокируется: маршруты `::/1` и `8000::/1` ведут
в туннель, и там такие пакеты отбрасываются. Так в обоих режимах полного туннеля;
в `external` `tt` дописывает эти половины в `tt.conf` и пишет об этом строкой
`[WG-EXT] сервер не выдал маршрута IPv6: …`.

Если IPv6 у вашего провайдера нет, ничего не меняется. Если есть, у блокировки
есть цена. Браузеры и большинство современных программ пробуют IPv6 и IPv4
параллельно и за доли секунды переходят на IPv4 — разницы не видно. Программа,
которая перебирает адреса по очереди и начинает с IPv6, будет ждать таймаута
соединения, иногда десятки секунд, и только потом попробует IPv4. Если это
мешает, отключите IPv6 у физического адаптера на время работы туннеля.

### Защита DNS

Windows рассылает DNS-запросы и резолверам других адаптеров, не только туннеля, —
без защиты имена посещаемых сайтов уходили бы провайдеру. Поэтому в `tun` и
`external`, пока туннель поднят, `tt` ставит фильтры брандмауэра Windows (WFP):
обращения на порт 53, UDP и TCP, разрешены только к DNS-серверам туннеля, к loopback
и самому `tt` — ему нужен DNS для доменов VK мимо туннеля. В выводе это строка
«защита DNS: пока туннель поднят, DNS системы — только к резолверам туннеля».

- Программа со своим резолвером, которая обращается на порт 53 к другому серверу,
  пока туннель поднят, получит отказ. Это и есть защита.
- DNS поверх HTTPS у браузеров идёт на порт 443, фильтр его не трогает, но идёт он
  по маршрутам через туннель — мимо туннеля не уходит.
- `dns = "doh:URL"` с именем хоста в адресе: имя самого DoH-сервера `tt` разрешает
  системным резолвером, при поднятом туннеле — через DNS туннеля. Это работает;
  пресеты `doh-*` начинаются с адресов, и их это не касается.

Фильтры живут в динамической сессии WFP: система снимает их вместе с процессом,
даже если `tt` убит. Если поставить их не удалось (например, остановлена служба
базовой фильтрации, BFE), `tt` откажет до подключения. Флаг
`-allow-dns-leak` разрешает подключиться без защиты — только на этот запуск,
в профиль он не записывается.

### Окно при переподключении

**В `tun` и `external`, пока туннель переподключается, трафик системы идёт мимо
туннеля** — с вашим настоящим адресом, а DNS — к резолверам провайдера.

Почему так. При переподключении VK может попросить капчу, а её страница открывается
в окне или в браузере. Это чужие процессы, и их соединения `tt` мимо туннеля не
уводит. Если бы маршруты оставались на мёртвом туннеле, страница капчи не загрузилась
бы, и туннель не поднялся бы никогда. Поэтому после неудачной попытки `tt` снимает
маршруты и защиту DNS, а адаптер оставляет; следующая успешная попытка их возвращает.
В выводе это видно так:

```
маршруты сняты на время переподключения — трафик и DNS системы идут мимо туннеля
…
маршруты возвращены — трафик системы снова идёт через туннель
```

Пока строки «маршруты сняты» нет, трафик мимо туннеля не идёт: когда туннель жив, но
сервер молчит (состояние «трафика нет»), маршруты стоят, и трафик просто не проходит.
Само окно обычно длится секунды — одна попытка и задержка перед следующей, от 1 до
64 с. Дольше оно бывает, когда пропала сеть: тогда туннель ждёт её возврата. Ещё один
известный случай — после пропажи сети VK иногда несколько минут не выдаёт новых
каналов TURN (с `-v` видно `Allocation Quota Reached`): туннель поднимется сам, но всё
это время трафик идёт мимо него.

Закроет это окно kill-switch — блокировка всего трафика, кроме туннеля и самого `tt`,
на время переподключения. Его пока нет. Если утечка в эти секунды для вас
недопустима, смотрите на строку «маршруты сняты» и не держите в это время открытым
то, что не должно уйти мимо туннеля.

### Если `tt` упал или был убит

Первый Ctrl+C останавливает туннель и убирает за собой всё. Второй Ctrl+C,
`taskkill /F` или падение убрать не дают, и тогда:

- **`tun`** — адаптер `tt`, маршруты через него и фильтры DNS исчезают вместе
  с процессом: адаптер снимает драйвер Wintun, фильтры — система. Убирать вручную
  нечего, новый `tt connect` можно запускать сразу. Остаётся только запись реестра
  с DNS бывшего адаптера (`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\{GUID}`):
  адаптера нет, поэтому ни на что она не влияет, а следующий запуск её перезапишет.
- **`external`** — служба и файл конфига могли остаться, и тогда весь трафик
  по-прежнему идёт в туннель, которого уже нет. Снимите службу командой
  `wireguard.exe /uninstalltunnelservice tt` и удалите
  `%APPDATA%\qwdtt-cli\tt.conf`. Фильтры DNS система сняла сама.

Что осталось в системе, показывает снимок `go run ./scripts/checktunnel` (раздел
«Отладка»).

## Восстановление

При обрыве клиент переподключается сам с нарастающей задержкой: 1, 2, 4 … 64 с.
В режимах `tun` и `external` `tt` ещё и следит за сетью. Смена сети — другой Wi-Fi,
кабель вместо Wi-Fi — перезапускает подключение сразу, без задержки, строкой
«сеть сменилась: …». Если сеть пропала, `tt` пишет «сеть пропала — туннель
переподключится, когда она вернётся» и перезапускает подключение, как только она
вернётся.

Хеш, по которому VK отвечает «звонок закрыт», исключается из перебора; когда годных
не остаётся, клиент останавливается с ошибкой — заведите новые через
`tt profile set <имя> -hashes`.

## Отладка

- `-v` — весь лог ядра и строка `[NETGUARD]` на каждое соединение `tt` мимо
  туннеля. Строки `[TUN]` и `[WG-EXT]` печатаются и без него.
- `TT_WG_DEBUG=1` — подробный лог самого WireGuard: рукопожатия, ошибки приёма.
  В PowerShell: `$env:TT_WG_DEBUG = 1; tt connect -v`.
- `go run ./scripts/checktunnel` — снимок системы, запускается из исходников. Windows
  и Linux. Показывает процессы `tt`, адаптеры, маршруты `/0` и `/1`, внешний адрес
  без прокси, кто отвечает на DNS; на Windows ещё фильтры WFP (без прав
  администратора их нет), записи реестра, службу и `tt.conf` режима `external`, на
  Linux — правила маршрутизации, таблицы nftables (только под `sudo`), `resolv.conf`
  и записи `resolvconf`, `rp_filter`. Ничего не меняет; снимки до запуска, во время и
  после остановки удобно сравнивать.

## Предупреждения

Релизные бинари не подписаны. Windows SmartScreen и антивирусы могут возражать
против программы, которая держит сетевой туннель, — это ожидаемо до появления
подписи. Исходники открыты, сборка воспроизводима скриптом из репозитория.
