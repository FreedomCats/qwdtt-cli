# Предложения в апстрим (SpaceNeuroX/proxy-turn-vk-android)

Черновики. Небольшие правки ядра мы сначала делаем у себя, потом предлагаем в апстрим.
Тексты можно копировать как есть.
Наши коммиты применяют их правилами `scripts/vendorcore/rules.go` — патч для апстрима
нужно собрать руками из `git diff` по `internal/core` (имена файлов те же, `go_client/`).

---

## 1. Закрытый звонок (error_code=954) классифицируется как `error`, а не `dead`

**Проблема.** VK на ссылку закрытого звонка отвечает `Invalid join link (error_code=954)`.
`fatalCallError` верно делает из этого `*CallUnavailableError`, но `classifyHashCheckError`
(`main.go`) смотрит только в текст ошибки и ищет `call not found`, `9000`,
`callunavailable` — в «Invalid join link» нет ни одной из этих строк. Статус — `error`.
Через путь vkcalls ошибка ещё и завёрнута в `vkCallsFailure`.

**Правка** (в начало `classifyHashCheckError`, после `if err == nil`):

```go
if callErr, ok := asCallUnavailableError(err); ok {
	return "dead", fmt.Sprintf("Звонок не найден или закрыт (error_code=%d)", callErr.Code)
}
```

`errors.As` проходит и через `vkCallsFailure` (у него есть `Unwrap`).

## 2. Группа без кредов не передаёт эстафету — следующие группы ждут вечно

**Проблема.** `WorkerGroup` (`group.go`) закрывает `signalReady` только после удачных кредов.
При ошибке кредов (мёртвый хеш, сеть) группа делает `return`, и следующая группа навсегда
остаётся в `select { case <-waitReady: … }`. При >9 воркерах (несколько групп) и мёртвом
хеше первой группы туннель не поднимается, хотя остальные хеши годны, и `Run` не кончается.

**Правка** — в ветке ошибки кредов, перед `return`:

```go
if signalReady != nil {
	close(signalReady)
}
```

## 3. Конфиг WireGuard держится на одном воркере (квота TURN, 486)

**Проблема.** Флаг `configRequestInFlight` берётся до входа в `RunSession`. Воркер, взявший
его и получивший `486 Allocation Quota Reached`, отпускает флаг и ждёт 30–60 с. Остальные
воркеры за это время уже вошли в сеансы с `getConf=false`, а решение принимается только в
начале сеанса — конфиг никто не просит, туннель не поднимается минутами при рабочих сеансах.
Наблюдалось после пропажи и возврата сети (аллокации умерших сеансов ещё держат квоту).

**Правка.** Конфиг просит каждый воркер, входящий в сеанс, пока он не получен:

```go
getConf := shouldGetConfig && atomic.LoadInt32(&configSent) == 0
…
if getConf && configDelivered {
	atomic.StoreInt32(&configSent, 1)
}
```

(флаг `configRequestInFlight` уходит). Сервер на повторный `GETCONF` отдаёт тот же конфиг —
ключи устройства создаются один раз (`server/connections.go`); лишний доставленный конфиг
`RunSession` уже сбрасывает («Конфиг уже был доставлен другим воркером»). Цена — `GETCONF`
вместо `AUTH` у воркеров, стартовавших до получения конфига.

Проверено стендом (pion TURN на loopback, `QuotaHandler` отвечает 486 первому воркеру с задержкой,
заглушка сервера на DTLS): со старой логикой конфиг не приходит — три сеанса, ни одного `GETCONF`;
с правкой — через 1,6 с.

Связанное: канал конфига получает только первая группа (`main.go`, `isFirst`). При мёртвом
хеше или исчерпанной квоте первой группы конфиг не придёт вовсе. У нас канал передаётся всем
группам; в апстриме — то же изменение в месте вызова `WorkerGroup`.

## 4. Счётчики пакетов, сброшенных ядром

**Проблема.** В десктопном режиме ядро выбрасывает пакеты молча: «туда» — `readLoop`, когда
очереди всех воркеров полны (счётчик `tunDroppedCount` только при `tunFile != nil`);
«обратно» — `RunSession`, ветка `default` у `d.ReturnCh <- pkt`, счётчика нет совсем. Потери
5–20% UDP при поднятом туннеле не на что списать.

**Правка.** `DroppedUp`, `DroppedDown atomic.Uint64` в `Stats`; `d.stats.DroppedUp.Add(1)` в
ветке «все workers перегружены», `stats.DroppedDown.Add(1)` в ветке `default`; числа — в
строку `[СТАТИСТИКА]` (у нас — в событие). Поведение не меняется.

## 5. Остановка ждёт воркер до 45 с или до 30 минут

**Проблема.** Отмена сеанса снимает соединение через `stopConn` (`context.AfterFunc` →
`SetDeadline(now)`), но в двух местах её обходит:

- `stopConn` ставится после запроса конфига, а `RequestConfig` ждёт ответа до 45 с. Отмена во
  время запроса ждёт ответа, которого не будет: relay уже снят;
- чтение сеанса перед каждым `Read` ставит дедлайн +30 мин и затирает дедлайн «сейчас», если
  `stopConn` успел раньше, — `Read` ждёт 30 минут.

Воркер, застрявший так, держит `WorkerGroup`, а за ней и всю остановку клиента.

**Правка.** Перед запросом конфига —

```go
stopConfig := context.AfterFunc(sessCtx, func() {
	_ = activeConn.SetDeadline(time.Now())
	_ = activeConn.Close()
})
```

и `stopConfig()` перед `[READY]`; в чтении сеанса — проверка после установки дедлайна:

```go
_ = activeConn.SetReadDeadline(time.Now().Add(sessionReadTimeout))
if sessCtx.Err() != nil {
	return
}
```

`AfterFunc` срабатывает после отмены, так что либо проверка её увидит, либо дедлайн «сейчас»
ляжет позже. Первое воспроизводится стендом из предложения 3 (заглушка не отвечает на
`GETCONF`, отмена — после запроса): без правки возврат через 45 с, с правкой — сразу. Второе
стенд поймал под `-race`, когда отмена пришла сразу после конфига.

  `vkRequestMu` на всё время, вместе с ожиданием капчи (см. [`architecture.md`](architecture.md), §08 и раздел задачи в §11).
