# Архитектура qwdtt-cli

Настольный **консольный** клиент к протоколу qWDTT: системный VPN поверх TURN-инфраструктуры
звонков VK. Один Go-бинарь, ядро подключено библиотекой, подменяемый datapath.

Конфигураторы сервера, деплой, админки, QR и подписки остаются в Android-приложении и в
настольный клиент не переносятся. Служба и автозапуск не делаются: клиент запускается из
консоли и живёт, пока живёт процесс.

- **Ядро:** qWDTT 1.4.3 (`SpaceNeuroX/proxy-turn-vk-android`), GNU GPL v3
- **Приоритет платформ:** Windows → Linux → macOS
- **План работ:** итоги этапов — §11. Подробные планы и журналы этапов (`plan-e1.md` …
  `plan-e5.md`, на них ссылаются текст и комментарии в коде) ведутся локально в `doc/local/`
  и в репозиторий не входят

## 01. На чём стоит проект

Архитектура опирается на проверенное поведение кодовой базы qWDTT, а не на предположения.

| Факт | Где | Следствие |
|---|---|---|
| Клиент собирается под win/linux/mac после правки 2 файлов | `listen.go`, `tun_fd.go` | Порт не нужен, нужна обвязка |
| `-mode socks` поднимает userspace WireGuard через gVisor netstack | `socks_wg.go`, `socks5.go` | Готовый datapath без TUN и без прав администратора |
| Сервер отдаёт WG-конфиг с `Endpoint = 127.0.0.1:<порт клиента>` | `server/wireguard.go:171` | Любой WireGuard-клиент подключается к ядру по loopback |
| Все исходящие сокеты ядра создаются в 6 местах через стандартные Go-примитивы | `session.go`, `creds.go`, `creds_vkcalls.go`, `doh.go` | Обход туннеля решается одним хуком `Control` |

Проверено сборкой:

```
windows/amd64   24.5 MB   OK
linux/amd64     24.3 MB   OK
darwin/arm64    23.5 MB   OK
```

Правки для кроссплатформенности: `listen.go` разбит на `_unix`/`_windows` (на Windows
`syscall.SetsockoptInt` принимает `syscall.Handle`, а не `int`). Второй файл, `tun_fd.go`,
сперва ограничивался `//go:build linux` с заглушкой для остальных платформ, а в задаче B6
перестал переноситься вовсе — вместе со всем режимом `rawtun`.

### Что берём и что нет

**Берём:** получение TURN-креды VK, нативный решатель капчи, TURN allocation и ChannelBind,
RTP-обфускацию и вывод WRAP-ключа, диспетчер и группы воркеров, протокол `GETCONF`/`AUTH`,
DoH-резолвер, keepalive и anti-replay.

**Не берём:** SSH-деплой сервера, admin API, Telegram-бот, QR, подписки и группы профилей,
bypass приложений, Kotlin-обвязку WebView-капчи (у нас своя — окно WebView2 на Windows и
браузер под управлением на Linux, §08), виджеты, автообновление APK, Wi-Fi-автопаузу, режим `rawtun`.

## 02. Семь решений

### Р1. Ядро подключается библиотекой, а не запускается подпроцессом

Android запускает `libclient.so` отдельным процессом и общается с ним текстом через
stdin/stdout. На десктопе берём те же файлы, но собираем в тот же бинарь: `package main`
становится `package core`, разбор флагов — структурой `core.Config`, маркеры stdout —
типизированными событиями.

**Причина.** Собственный трафик ядра — запросы к VK, DoH и TURN-relay — обязан идти *мимо*
туннеля, иначе он замыкается сам на себя. На Android это делает `addDisallowedApplication`
для своего же пакета. На Windows единственный надёжный аналог — установить `IP_UNICAST_IF`
на каждом сокете ядра, а **сделать это через границу процесса невозможно**. Библиотека —
не удобство, а необходимое условие полного туннеля.

### Р2. Datapath — интерфейс с тремя реализациями

Способ доставки трафика в туннель отделён интерфейсом `datapath.Datapath`. Реализации:
`socks` (netstack, без прав), `tun` (настоящий адаптер: Wintun на Windows, `/dev/net/tun` на
Linux; прежнее имя `wintun` — синоним), `external` (штатный WireGuard читает наш конфиг,
только Windows).

**Причина.** Позволяет выпустить рабочий продукт на первой неделе (`socks` не требует ни
администратора, ни платформенного кода), а сложный `tun` добавить вторым этапом, не
переписывая ничего выше. Все три используют один и тот же wireguard-go и отличаются только
реализацией TUN.

### Р3. Обход туннеля — один хук в шести точках

Пакет `netguard` даёт одну функцию сигнатуры
`func(network, address string, c syscall.RawConn) error` — метод `Guard.Control`. CLI
передаёт её ядру полем `core.Config.DialControl`, а ядро подставляет в поле `Control`
у `net.Dialer` в шести местах (§05).

**Причина.** Go предоставляет один и тот же хук `Control` для всех способов создания сокета,
а pion/turn принимает уже готовый `net.PacketConn` через поле `Conn`. Платформенная логика
живёт ровно в одном файле на ОС.

### Р4. Свой Bind у wireguard-go в процессе, loopback — только для `external`

В Э1 и Э2 wireguard-go соединялся с ядром через UDP на `127.0.0.1:9000`, как и на
Android. В Э3 (блок B) у `socks` и `tun` свой `conn.Bind` — `datapath.Pipe`: пакеты
идут между wireguard-go и диспетчером ядра в памяти, ядро получает свою сторону готовым
`net.PacketConn` (`core.Config.PacketConn`). `external` остаётся на loopback:
wireguard.exe — чужой процесс.

**Причина.** Порт ядра на loopback открыт любому процессу машины, а диспетчер ядра
отвечает адресу последнего отправителя (`clientAddr`): один посторонний датаграм уводил
ответы сервера, и туннель стоял до следующего пакета wireguard-go. Заодно минус хоп и
два системных вызова на пакет, и нет `WSAECONNRESET` на Windows от ICMP «порт
недоступен» (§04). Правок апстрима не понадобилось: сокет ядра открывает наш `run.go`.

### Р5. Капча: нативно, затем WebView2, затем руками

Цепочка повторяет логику Android, заменяя только последнее звено: нативный решатель Go v2
(2 попытки) → окно капчи: WebView2 на Windows, браузер на Chromium под управлением по CDP на
Linux → ручной режим: страница капчи в браузере системы, токен человек переносит в терминал
(§08).

**Причина.** WebView2 — прямой аналог Android WebView: в страницу встраивается тот же
перехватчик ответа VK, и токен приходит в программу сам; среда выполнения предустановлена
в Windows 11. На Linux WebView2 нет, а встроенный движок требует cgo — окно даёт
установленный браузер на Chromium, токен снимается по протоколу DevTools. Без такого
браузера, как и на macOS, — нативный решатель плюс ручной режим.

### Р6. Профили в TOML, секреты — в DPAPI

Двадцать пять флагов заменяются файлом профилей. Пароль подключения и хеши VK не лежат
в открытом виде: на Windows шифруются через `CryptProtectData` и привязываются к учётной
записи.

**Причина.** Пароль подключения — это одновременно WRAP-ключ: из него выводится ключ
RTP-обфускации (`wrap.go`, HKDF-SHA256). Его утечка равна компрометации всего транспорта,
а не только авторизации.

### Р7. Ядро вендорится дословно, правки выносятся наружу

Файлы qWDTT кладутся в `internal/core/` с минимальными изменениями. Всё новое — в отдельных
файлах `api.go`, `events.go`, `netguard_hook.go`. Внутри апстримных файлов допускаются только
механические замены: `log.Printf` → `logf`, `fmt.Printf(маркер)` → `emit(...)`,
`main()` → `Run(cfg)`.

**Причина.** qWDTT активно развивается. Чем ближе вендор к апстриму, тем дешевле переносить
обновления. Механический характер правок позволяет описать перенос скриптом.

> **Как это устроено сейчас.** Перенос — `go run ./scripts/vendorcore`, все правки
> апстримного кода — правила в `scripts/vendorcore/rules.go` (шаблон и обязательное число
> совпадений: апстрим переписал строку — перенос падает, а не теряет правку молча). Кроме
> механических замен там теперь и исправления ошибок ядра — решение пользователя: небольшие
> правки делать у себя, потом предлагать в апстрим (черновики — `upstream-proposals.md`):
> 954 → `dead` по типу ошибки, счётчики сброшенных пакетов, конфиг WireGuard от любого
> воркера и любой группы, передача эстафеты группой без кредов, окно ручной капчи 180 с.
> То, что держится на коде апстрима без правки, сторожат тесты: `TestNetguardCoverage`
> (новые сокеты ядра) и `TestCaptchaRequestsSerialized` (капчу просят только под замком
> кредов, §08). Проверка, что `internal/core` совпадает с апстримом и правилами, —
> `vendorcore -check`. Обновление ядра: клон апстрима, `git checkout` нужного коммита,
> `go run ./scripts/vendorcore -upstream <клон>`, затем `-check`. Новые коммиты апстрима
> после нашего (из `CORE_VERSION`) — `git log <коммит>..` в клоне.

Служебные команды пишутся на Go — пакет `main` в `scripts/<имя>/`, запуск
`go run ./scripts/<имя>`. Прежние скрипты на PowerShell переведены (§11, «Вне этапов»).

Зависимость идёт строго сверху вниз: `cli` собирает всё, `supervisor` знает про `core`
и `datapath`, `datapath` и `netguard` — про `winsys` на Windows и `linuxsys` на Linux. `core` не знает
ни о `netguard`, ни о `datapath`: хук приходит к нему полем `Config.DialControl`. `winsys`
и `linuxsys` не знают ни о чём.

## 04. Datapath

Ядро всегда делает одно и то же: принимает пакеты WireGuard и уносит их через TURN.
Различается только то, что их подаёт. Свой wireguard-go (`socks`, `tun`) отдаёт их
каналом в памяти (`Pipe`, Р4), wireguard.exe (`external`) — UDP на loopback ядра.

```go
type Datapath interface {
    // Start получает WG-конфиг, который сервер вернул в GETCONF.
    Start(ctx context.Context, conf *WGConfig) error
    // Endpoint — из конфига; ядро слушает его только у external.
    Endpoint() netip.AddrPort
    // Requires — что нужно для запуска: права, файлы, внешние программы.
    Requires() Requirements
    Close() error
}

type Requirements struct {
    Unsupported error    // почему не работает на этой системе — проверяется первым
    Admin       bool     // нужны права администратора
    Files       []string // файлы рядом с бинарём — wintun.dll (на Linux пусто)
    Programs    []string // внешние программы — wireguard.exe
    Netguard    bool     // забирает весь трафик: сокеты ядра — мимо туннеля (§05)
    DNSGuard    bool     // нужна защита от утечки DNS (§09)
    Warning     string   // ограничение, о котором надо предупредить при запуске
}
```

Необязательные части интерфейса — две появились в Э2 ради `tun`, третья в Э3:

- `Persistent` — реализация живёт весь `qwdtt-cli connect`, а не одну попытку: пересоздавать
  адаптер на каждое переподключение значило бы, что он исчезает и появляется, а Windows
  заводит «Сеть 2», «Сеть 3». Супервизор строит её один раз; повторный `Start`
  перенастраивает устройство новым конфигом сервера, `Suspend` после неудачной попытки
  снимает маршруты и защиту DNS, а адаптер оставляет (§07, §09).
- `Reserver` — занять общее на машину до подключения. У `tun` это мьютекс
  адаптера на Windows и абстрактный unix-сокет `@qwdtt-cli-tun` на Linux (уходит с
  процессом): второй запуск отказывает сразу, а не после VK и TURN, где супервизор
  принял бы отказ за сбой попытки.
- `Piped` (Э3) — `CoreConn() net.PacketConn`: datapath со своим wireguard-go отдаёт ядру
  сторону канала в памяти. `Pipe` — сам `conn.Bind` и живёт с устройством (у `tun` —
  весь сеанс, переживает `BindUpdate`); сторона ядра новая на каждую попытку, прежняя
  закрывается. Полная очередь (1024) сбрасывает пакет, как сокет UDP, и считает сброс
  (`Pipe.Dropped`).

`WGConfig` — разобранный ответ сервера (`datapath.ParseWgQuick`), в котором рядом с полями
лежит и исходный текст: `socks` собирает из полей запрос к `wireguard-go`, `external`
пишет в файл текст как есть. Настройки самой реализации — адрес SOCKS5, учётные данные,
пути — передаются её конструктору, а не через интерфейс.

| Реализация | Как доставляет трафик | Права | Зависимости | Охват | Этап |
|---|---|---|---|---|---|
| `socks` | gVisor netstack + SOCKS5 на `127.0.0.1:1080` | не нужны | нет | только приложения с поддержкой прокси | Э1 |
| `external` | пишет `qwdtt-cli.conf`, вызывает `wireguard.exe` | админ | установленный WireGuard | весь трафик системы | Э1 |
| `tun` | свой адаптер + wireguard-go в процессе | админ / root | Windows — `wintun.dll` рядом с exe; Linux — ядро 5.12+ | весь трафик системы | Э2 (Windows), Э4 (Linux) |

`socks` и `tun` отличаются тем, откуда берут TUN: первый создаёт его через
`netstack.CreateNetTUN`, второй — на Windows через `tun.CreateTUNWithRequestedGUID` поверх
Wintun (постоянный GUID, чтобы Windows узнавала адаптер между запусками), на Linux — через
`tun.CreateTUN` (`/dev/net/tun`). Платформа отдаёт общей логике `Start`/`Suspend`/`Close`
набор функций — `configure`, `addRoutes`/`removeRoutes`, `flush`, `release`; сама логика и её
тесты от системы не зависят. Дальше и там и там
работает один и тот же запуск wireguard-go (`wgdevice.go`). Модуль `golang.zx2c4.com/wintun` уже присутствует в дереве
зависимостей qWDTT.

> **Ограничение socks-режима.** SOCKS5 в ядре обслуживает только TCP CONNECT и намеренно
> отклоняет IPv6 (`socks5.go`). Это не полноценный VPN: DNS-запросы приложения пойдут мимо
> туннеля, если приложение не проксирует их само. Режим позиционируется как «браузер и то,
> что умеет прокси», а не как замена `tun`.

## 05. netguard — обход туннеля

Центральная часть проекта. Когда `tun` или внешний WireGuard забирает весь трафик системы,
собственные сокеты ядра тоже попадают в туннель — и туннель начинает зависеть от самого себя.
Соединение не поднимется никогда.

```
ДОРОЖКА 1 — ТРАФИК ПРИЛОЖЕНИЙ

 Приложения → адаптер qwdtt-cli → wireguard-go → Pipe (в памяти) → Диспетчер → RTP-обфускация
                                                                   9…108 воркеров     │
                                                                                      ▼
                                                                                TURN-relay VK
                                                                      (выглядит как медиапоток WebRTC)

                                                                               ваш VPS :56000

 Сокеты ядра  →  netguard         →  Физический адаптер  →  Интернет
 VK HTTPS        IP_UNICAST_IF       Wi-Fi / Ethernet
 DoH             на индекс
 TURN UDP/TCP    физ. адаптера

 Без netguard сокеты ядра уходят в адаптер qwdtt-cli → петля, туннель не встаёт.
```

Дорожка 2 существует только ради того, чтобы дорожка 1 могла подняться.

### Шесть точек внедрения

| # | Где | Что закрывает | Правка |
|---|---|---|---|
| 1 | `session.go` · `dialTURNConn` | TURN по UDP | `net.DialUDP` → `net.Dialer{Control}` |
| 2 | `session.go` · та же функция | TURN по TCP | `Control` в существующий `net.Dialer` |
| 3 | `creds.go` · `setupGlobalResolver` | резолвер VK по UDP/TCP :53 | `Control` в существующий `net.Dialer` |
| 4 | `doh.go` · `newDoHBootstrapDialer` | соединения DoH | `Control` в существующий `net.Dialer` |
| 5 | `creds.go` · `getTokenChain` | HTTPS к VK с отпечатком Chrome | `tlsclient.WithDialer(…)` |
| 6 | `creds_vkcalls.go` · `getVKCredsViaVKCalls` | HTTPS к VK в режиме аккаунта | то же |

Шестая точка нашлась при сверке с кодом перед Э2. Правки в апстримные файлы вносят
правила `scripts/vendorcore/rules.go` (Р7), сами диалеры живут в нашем `netguard_hook.go`. Резолв
имён в точках 1, 5, 6 и внутри pion/turn идёт через `net.DefaultResolver`, который ядро
подменяет в точках 3 и 4, — значит, и он под хуком. Решатель капчи берёт HTTP-клиента
из точки 5. Loopback для datapath (`listen.go`, теперь только у `external`) хук не получает; у `socks`
и `tun` сокета нет вовсе (Р4). Полноту списка сверяет
`TestNetguardCoverage`: новая точка после обновления ядра роняет тест, а не туннель.

`bogdanfinn/tls-client` 1.15.1 экспортирует `WithDialer`, `WithDialContext` и
`WithLocalAddr` — подмена диалера поддерживается штатно, форк не нужен.

### Что проверено в Э2

- `IP_UNICAST_IF` действует и на TCP, и на UDP: сокет с индексом loopback до внешнего
  адреса не доходит, с индексом физического адаптера — уходит через него.
- Если для семейства физического интерфейса нет (сеть без IPv6), сокет этого семейства
  не создаётся, а не уходит по общей таблице: при поднятом туннеле она ведёт в туннель.
  Go переходит к следующему адресу, и ядро уходит на IPv4.

> **Ловушка Windows.** `IP_UNICAST_IF` для IPv4 принимает индекс интерфейса в **сетевом**
> порядке байт, а `IPV6_UNICAST_IF` для IPv6 — в **машинном** (так же в wireguard-go,
> `conn/bind_windows.go`). На Windows 11 перепутанный порядок не молчит, а роняет
> `setsockopt` (`WSAEADDRNOTAVAIL`, `WSAEINVAL`): малый индекс после перестановки байт
> становится несуществующим. На старых сборках опция, по сообщениям, молча игнорируется,
> и туннель просто не поднимается. Тесты `netguard` ловят оба исхода.

Физический интерфейс выбирает `winsys.DefaultInterface` — перенос `findDefaultLUID` из
wireguard-windows (`tunnel/mtumonitor.go`): маршрут с длиной префикса 0, интерфейс в
состоянии `Up`, не свой адаптер, наименьшая сумма метрик маршрута и интерфейса.
Маршруты туннеля — половины `/1`, в выбор они не попадают, поэтому выбор верен и при
поднятом туннеле. `GetBestRoute2` до внешнего адреса, как предполагалось сперва, для
этого не годится: при поднятом туннеле лучший маршрут ведёт в туннель.

О смене сети `winsys.WatchNetwork` узнаёт по уведомлениям об изменении маршрутов и
IP-интерфейсов (`winipcfg`). `netguard.Guard.Watch` сворачивает серию событий — 2 с
тишины, но не дольше 10 с от первого, — пересчитывает выбор и, если он сменился, ставит
новые индексы до того, как сообщить: новые сокеты сразу берут новый интерфейс, уже
открытые доживают со старым. Пропажа сети попытку не перезапускает, её перезапускает
возврат сети: выдернутый и вставленный кабель даёт один перезапуск (§07).

### Linux (Э4)

Та же модель, другие средства (`netguard_linux.go`, `linuxsys`):

- **Привязка — `SO_BINDTOIFINDEX`** (ядро 5.0+, принимает индекс, как `IP_UNICAST_IF`), на
  старом ядре — `SO_BINDTODEVICE` по имени. Работает без прав и побеждает маршрут `/1` в
  TUN (опыт N1). fwmark и `ip rule` отвергнуты: правила переживают падение процесса.
- **Выбор интерфейса** — `linuxsys.DefaultInterface`: маршрут `/0` таблицы `main`,
  интерфейс поднят и со связью, не свой адаптер, наименьшая метрика маршрута.
- **Смена сети** — `linuxsys.WatchNetwork`: подписки netlink на маршруты, интерфейсы и
  адреса; оборвавшаяся подписка (ENOBUFS) возобновляется и считается событием. Свёртку
  серии делает тот же `Guard.Watch`.
- **Метка `SO_MARK`** (`netguard.SocketMark`) ставится сокетам ядра, только когда включена
  защита DNS: по ней таблица nftables пропускает DNS для VK (§09а). Маршрутизации по метке
  нет.
- **Обратный фильтр.** Ответы VK и TURN приходят на физический интерфейс, а обратный
  маршрут к источнику ведёт в `qwdtt-cli`: строгий `rp_filter` их отбрасывает. `qwdtt-cli` `sysctl` не
  меняет, а отказывает до подключения с подсказкой `rp_filter=2` (действует большее из
  `all` и значения интерфейса). Строгий фильтр IPv6 firewalld (`IPv6_rpfilter`,
  умолчание) — то же для IPv6, поэтому при нём сокетам ядра даётся только IPv4
  (`Guard.NoIPv6`).

## 06. API ядра

Текстовый протокол между Kotlin и Go исчезает. Шесть маркеров stdout становятся
типизированными событиями, пять команд stdin — четырьмя методами `Control`: пятая,
`STOP`, не нужна, её работу делает отмена `ctx`.

```go
// Три точки входа вместо трёх веток func main(). Останавливаются отменой ctx,
// код возврата процесса собирает CLI из возвращённой ошибки.
func Run(ctx context.Context, cfg Config, sink Sink, ctrl *Control) error
func RunPing(ctx context.Context, cfg Config, sink Sink) error
func RunHashCheck(ctx context.Context, cfg Config, sink Sink) error

type Sink interface { Emit(Event) }

// Набор реализаций Event закрыт: метод-маркер неэкспортируемый, чтобы снаружи
// нельзя было добавить тип, о котором не знает ни один разбор.
type Event interface { isCoreEvent() }

// Ручку управления создаёт вызывающий и передаёт в Run: Run возвращается только
// вместе с туннелем, отдать её сам он не успел бы. nil означает, что управлять
// ядром не понадобится. Место ей не в Config: настройки копируют, приводят
// к канону и читают из профиля, а здесь состояние, общее у нескольких горутин.
type Control struct { /* ... */ }

func NewControl() *Control
func (c *Control) Pause()
func (c *Control) Resume()
func (c *Control) SubmitCaptcha(token string)
func (c *Control) SubmitTurnCreds(creds TurnCreds)
```

`Pause` придерживает только те группы воркеров, которые ещё не сходили за кредами VK:
флаг проверяется в одном месте, перед запросом. Поднятый туннель пауза не рвёт — в Android
эта команда приходила при уходе в doze-режим, где незачем начинать новые сессии. `Stop`
не нужен: его роль играет отмена `ctx`, переданного в `Run`.

| Было (текст в stdout) | Стало (Go) | Кто обрабатывает |
|---|---|---|
| `CAPTCHA_SOLVE\|…` | `EventCaptchaRequired` | `captcha` |
| `VK_AUTH_REQUIRED\|…` | `EventVkAuthRequired` | `supervisor` → пользователь |
| `HASH_CHECK\|…`, `HASH_CHECK_START\|…` | `EventHashCheck` | `cli` (`qwdtt-cli hashes`) |
| `PING_RESULT\|…`, `PING_ERROR\|…` | `EventPing` | `cli` (`qwdtt-cli ping`) |
| рамка с WG-конфигом в stdout | `EventConfig` | `datapath` |
| `log.Printf` со всеми префиксами | `EventLog{Level,Tag,Msg}` | `log` → консоль |

Дополнительно ядро начинает публиковать то, что на Android выводилось только в лог:
`EventStage` для шагов подключения, `EventStats` для счётчиков и `EventHashFailed` —
группа воркеров не получила креды по своему хешу звонка. Последнее нужно супервизору,
чтобы исключить негодный хеш из следующей попытки и остановиться, когда годных
не осталось (§07); туннель от одного такого отказа не падает. Шаги повторяют
`ConnectionStep` из Android один в один — DNS, VK, капча, WRAP, TURN, DTLS, воркеры,
VPN/SOCKS, готово.

Отправляет их не одно только ядро. Ядру принадлежит середина — VK, капча, WRAP,
TURN, DTLS, воркеры; края принадлежат супервизору, потому что ядро о них не знает:
DNS проверяется до его запуска, а VPN, SOCKS и готово закрываются после того, как
datapath поднимет туннель по `EventConfig`. На Android разделение ровно такое же.

Повторы ядро глушит само: воркеров до 108, и каждый проходит TURN и DTLS
самостоятельно, поэтому наружу уходит первый, добравшийся до пары (шаг, статус).
А вот порядок шагов ядро намеренно не выравнивает — WRAP закрывается на старте,
раньше VK, потому что ключ выводится из пароля, а не из ответа VK. Складывать из
событий схему подключения — дело супервизора (§07).

Реализация — `internal/core/events.go`. Правки, которыми маркеры заменены на
события внутри апстримного кода, живут в `scripts/vendorcore/rules.go`: иначе они не
переживут обновление ядра (Р7).

`EventStats` несёт и `DroppedUp`/`DroppedDown` — пакеты, выброшенные ядром из-за
полных очередей (к воркерам и к WireGuard), нарастающим итогом за `Run`. В апстриме их не
считали вовсе; `connect -v` печатает их в строке счётчиков, при остановке — итог за все
попытки, если он не ноль.

## 07. Супервизор

В Android это 2162 строки `TunnelManager.kt` с watchdog, разбором лога и парой десятков
состояний UI. В консоли остаётся конечный автомат и политика перезапуска.

```
Idle ──▶ Resolving ──▶ Captcha ──▶ VK ──▶ TURN ──▶ Handshake
            ▲                                          │
            │           ┌──────────────────────────────┘
            │           ▼
            │      Configuring ──▶ Connected ◀──▶ Degraded
            │                          │              │
            └──── Reconnecting ◀───────┴──────────────┘

Stopping ◀── из любого состояния: Ctrl+C или годных хешей не осталось
```

- **Линия подключения проходится только вперёд.** Порядок шагов ядро не выравнивает
  (§06), поэтому автомат считает состоянием самый далёкий достигнутый шаг. Без этого
  правила поздний отказ DTLS одного воркера из ста вернул бы поднятый туннель
  в «рукопожатие». Капча стоит на линии раньше VK: шаг `vk` ядро закрывает, только
  когда креды получены, а капчу просит по ходу запроса. У шага `wrap` своего состояния
  нет вовсе — он закрывается на старте, раньше всех. Шаги `workers`, `vpn` и `socks`
  ведут в одно `Configuring`: для пользователя это одна фаза.
- **Отказ шага состояния не меняет.** Ядро повторяет шаги само — капчу трижды, TURN
  и DTLS каждым воркером, — и закончилась попытка или нет, знает не шаг, а возврат
  из `core.Run`. Отказ только помечает шаг в таблице, чтобы было что показать.
- **Backoff** переносится из Android дословно: `1 · 2^попытка` секунд, счётчик попыток
  ограничен шестью — то есть 1, 2, 4, 8, 16, 32, 64 с и дальше по 64 с.
- **Degraded** — воркеры живы, но нисходящего трафика нет дольше 25 секунд. Та же величина,
  что у `hasRecentTransportActivity` на Android. Отсчёт идёт от начала неотвеченной
  отправки: от последнего нисходящего байта простаивавший туннель объявлялся бы сломанным
  первым же запросом, а от последнего восходящего молчание сервера не обнаружилось бы
  вовсе — пока приложение отправляет, отсчёт сбрасывался бы каждые три секунды. Из него
  есть путь и обратно в `Connected`: молчание такой длины бывает и у живого туннеля,
  и считать его отказом значило бы рвать рабочее соединение. Отсчёт начинается не с
  первого неотвеченного байта, а когда неотвеченная отправка набрала килобайт: keepalive
  WireGuard в 32 байта раз в 25 секунд сервер по протоколу не отвечает, и без порога
  простаивающий туннель перезапускался бы каждые 50 секунд (найдено живым прогоном).
- **Reconnecting ведёт в `Resolving`**, а не в `Configuring`: перезапуск — это новый
  `core.Run`, то есть новая попытка с самого начала, с очисткой таблицы шагов.
- **Смена сети** приходит из `winsys` (уведомления о маршрутах и IP-интерфейсах), серию
  событий сворачивает `netguard` (§05) — иначе переключение Wi-Fi → Ethernet вызывает три
  перезапуска подряд. `Tunnel.Restart` обрывает текущую попытку или будит из задержки:
  новая попытка — сразу и со сброшенным счётчиком, новая сеть — не повод ждать 64 с.
  За сетью следят только `tun` и `external`: `socks` трафик системы не забирает.
- **Datapath на попытку или на сеанс.** `socks` и `external` строятся на каждую попытку
  и закрываются вместе с ней. `tun` (`Persistent`, §04) строится один раз: после
  неудачной попытки, до задержки, супервизор зовёт `Suspend` — маршруты и защита DNS
  снимаются, адаптер остаётся, — а следующий успешный `Start` их возвращает. Не снялись
  маршруты — datapath закрывается целиком, следующая попытка строит новый. У `Piped`
  (§04) супервизор перед каждым `core.Run` кладёт в `Config.PacketConn` новую сторону
  канала.
- **Строки окна.** С kill-switch (§09) — «туннель переподключается — трафик системы
  заблокирован (kill-switch)» и «туннель снова поднят — трафик системы идёт через него»;
  без него — «маршруты сняты на время переподключения — трафик и DNS системы идут мимо
  туннеля» и «маршруты возвращены…». Какую печатать, супервизор спрашивает у CLI
  (`Options.KillSwitch`); `socks` трафик системы не забирает, строк нет.
- **Отказ хеша VK** не роняет туннель: группа, не получившая креды, возвращается сама и
  передаёт эстафету следующей (раньше не передавала — следующие группы ждали вечно);
  остальные работают, и конфиг WireGuard может прийти от любой из них. Хеш со статусом
  `dead` (звонок не найден или закрыт — в том числе 954, по типу ошибки ядра) исключается
  из следующих попыток; прочие отказы — капча, лимит, сеть — временные. Годных хешей не
  осталось — туннель останавливается, `connect` подсказывает `profile set <профиль>
  -hashes`, меню само спрашивает новые ссылки.

Состояние видно только в выводе самого `qwdtt-cli connect`: смена состояния печатается строкой,
счётчики трафика и аптайм обновляются в статусной строке. Отдельного канала для опроса
извне нет — клиент консольный и работает на переднем плане, смотреть на него можно там же,
где он запущен.

Реализация — `internal/supervisor`: `state.go` — автомат, `restart.go` — backoff и watchdog,
`lifecycle.go` — завершение.

## 08. Капча: нативный решатель, окно капчи и ручной режим

VK показывает Smart Captcha при получении TURN-креды. Нативный решатель в qWDTT закрывает
большинство случаев: считает proof-of-work и проходит слайдер прямо в Go. Но резервный путь
нужен, и на Android им был WebView.

| Шаг | Механизм | Windows | Linux / macOS |
|---|---|---|---|
| 1 | нативный Go v2, 2 попытки | есть | есть |
| 2 | на Android — невидимый автопрогон WebView, 2 × 10 с | нет (см. ниже) | нет |
| 3 | нативный Go v2, финальная попытка | есть | есть |
| 4 | окно капчи | окно WebView2; без Runtime — ручной режим | браузер на Chromium под управлением по CDP; без него — ручной режим |

Шаги 1–3 повторяют логику `creds.go` без изменений. Различается четвёртый: на Windows
открывается окно WebView2 (`github.com/jchv/go-webview2`) — точный аналог Android. На
Linux `qwdtt-cli` запускает установленный браузер на Chromium со своим временным профилем и
забирает токен по протоколу DevTools (`internal/captcha/browser_linux.go`, `cdp.go`; §11,
«Капча в браузере под управлением»). В обоих случаях человек только решает капчу.
Без окна (Windows без WebView2 Runtime, Linux без браузера на Chromium, вход по SSH, macOS)
четвёртый шаг — ручной режим (`internal/captcha/manual.go`):

1. `qwdtt-cli` сам открывает страницу капчи в браузере системы — на Linux через `xdg-open`,
   под `sudo` от имени вызвавшего пользователя (§09а). Не открылся браузер (SSH, нет
   графики) — ссылка напечатана, открыть её можно где угодно.
2. В терминале печатается однострочник для консоли браузера (F12 → Console): он ставит тот
   же перехватчик ответа VK, что окно WebView2.
3. Человек решает капчу; перехватчик печатает в консоли браузера строку
   `qwdtt-cli-captcha token <токен>`.
4. Эту строку (или один токен) человек вставляет в терминал `qwdtt-cli`.

Перенос токена руками нужен потому, что браузер системы — чужой процесс: забрать токен из
него программе нечем, а в адресной строке его нет (врезка ниже). Окно ручного режима — 180 с
вместо 60 у Android.

> **Уточнение после разведки (задача E1).** Токен, который ждёт ядро, — это `success_token`
> из **тела** ответа VK на `captchaNotRobot.check`, а не параметр в адресной строке.
> Android доставал его инъекцией JS в WebView, перехватывая `fetch` и `XMLHttpRequest`
> (`CaptchaWebViewManager.kt:70–120`). Редиректа с токеном в URL у VK нет вовсе, поэтому
> первоначальный план четвёртого шага — «пользователь вставляет URL редиректа в консоль» —
> нереализуем. Чем его заменить, решается в задаче E2; окно WebView2 на Windows это
> не затрагивает, оно перехватывает ответ так же, как Android. Чем заменить четвёртый шаг
> на не-Windows и стоит ли переносить WebView2 из Э2 в Э1 — разобрано в `e2-captcha.md`.

> **Просьбы капчи идут по одной.** Ответ у ядра — один глобальный
> канал с буфером 1, без привязки к просьбе. Это безопасно только потому, что двух просьб
> разом не бывает: капчу просят только из `fetchVkCreds`, а его зовёт только
> `fetchVkCredsSerialized` под `vkRequestMu` — на всё время, вместе с ожиданием ответа. Так же
> у makriq и PWDTT. Сторож — `TestCaptchaRequestsSerialized` (граф упоминаний функций по
> исходникам ядра): упадёт, если апстрим позовёт капчу мимо замка. `ErrBusy` диспетчера
> значит одно: решатель не уложился в срок прошлой просьбы, а ядро уже шлёт следующую.

Каркас решателя — `internal/captcha/solver.go`: интерфейс `Solver`, разбор
`EventCaptchaRequired` в просьбу со сроком и ответ ядру через `core.Control.SubmitCaptcha`.
Срок ядро не присылает, он считается по режиму (`core.CaptchaTimeout`): 10 с у `auto`,
60 с у `manual`, 120 с у `selected`. Человека на десятисекундное окно не зовут — отказ
уходит сразу, и ядро идёт дальше своей цепочкой, а не стоит впустую.

> **Сделано в Э1 (задача E3).** Шаг 4 на Windows — окно WebView2
> (`internal/captcha/webview2_windows.go`); CLI откатывается на консоль, если Runtime
> нет или `qwdtt-cli` запущен по SSH. Шаг 2 окном не делается и делаться не будет: на Android
> это был невидимый автопрогон WebView, а наше окно ждёт человека, которому десяти
> секунд мало, — диспетчер отказывает ядру сразу, и оно идёт к шагу 3.

> **Зависимость.** WebView2 Runtime предустановлен в Windows 11 и в актуальных сборках
> Windows 10, но не гарантирован. Если среда не найдена, шаг 2 пропускается, а шаг 4
> переключается на ручной режим — деградация, а не отказ.

## 09. Специфика Windows

### Права и запуск

`socks` работает от обычного пользователя. `tun` требует администратора: создание адаптера
обращается к драйверу. Бинарь собирается без манифеста `requireAdministrator` — вместо этого
CLI (`internal/cli`) проверяет токен процесса и, если прав не хватает именно для выбранного datapath,
объясняет это одной строкой и предлагает `socks`.

Клиент работает только на переднем плане: пока запущен `qwdtt-cli connect`, туннель поднят; по
Ctrl+C он корректно снимается. Службы Windows и автозапуска нет — это сознательное решение,
а не пробел. Второй `qwdtt-cli connect -datapath tun` на той же машине отсекается до
подключения именованным мьютексом `Global\qwdtt-cli-wintun`.

### Маршруты

Дефолтный маршрут не удаляется. Вместо этого через адаптер `qwdtt-cli` с метрикой 0 ставятся
`0.0.0.0/1`, `128.0.0.0/1`, `::/1` и `8000::/1` — они выигрывают у `/0` по длине префикса
и перекрывают всё адресное пространство обоих семейств. Исходный шлюз остаётся в таблице
нетронутым, поэтому `netguard` может увести трафик ядра наружу, а откат при падении
процесса сводится к исчезновению адаптера: адаптер снимает драйвер Wintun, маршруты
уходят вместе с ним (проверено `taskkill /F`).

- **Набор всегда полный** и от `AllowedIPs` сервера не зависит: что сервер не разрешил,
  уходит в туннель и отбрасывается wireguard-go, а не идёт тихо мимо туннеля. Неполные
  `AllowedIPs` — строка-предупреждение при подъёме.
- **IPv6 уходит в туннель, даже если сервер не выдал адреса IPv6**: такие пакеты
  wireguard-go отбрасывает, и программы откатываются на IPv4. Иначе весь IPv6 машины шёл
  бы мимо туннеля с настоящим адресом. Цена — таймауты у программ без Happy Eyeballs
  там, где IPv6 есть (README, раздел «IPv6»).
- **`external`** получает то же через `qwdtt-cli.conf`: `/0` из конфига сервера записывается
  половинами `/1`, без маршрута IPv6 от сервера дописываются `::/1, 8000::/1`. С `/0`
  wireguard-windows включил бы свой kill-switch (`tunnel/addressconfig.go`,
  `enableFirewall`: единственный пир с префиксом длины 0) и отрезал бы сокеты `qwdtt-cli.exe`.
- **Маршруты снимаются на время переподключения**, адаптер остаётся (`Suspend`, §04,
  §07). Причина — капча: её страница открывается в WebView2 или в браузере, это чужие
  процессы, `netguard` их не касается, и с маршрутами на мёртвом туннеле страница не
  загрузится, а капчу ядро просит как раз при переподключении. Без kill-switch на это
  время трафик и DNS системы идут мимо туннеля (строки «маршруты сняты…» и «маршруты
  возвращены…»); с ним (по умолчанию) окно закрыто — см. «Kill-switch» ниже.

### DNS и утечки

DNS туннеля ставится на адаптер (`SetInterfaceDnsSettings` через `winipcfg`). Перед
закрытием адаптер сбрасывается целиком — адреса, маршруты, DNS, — иначе DNS туннеля
остаётся в реестре под GUID адаптера (`Tcpip\Parameters\Interfaces`); так же делает
wireguard-windows. После падения сбросить его некому, но без адаптера он ни на что не
влияет и перезаписывается следующим запуском.

Одного DNS на адаптере мало: Windows 10 и новее опрашивает резолверы всех интерфейсов —
параллельно и при откате по таймауту. Отключение smart multi-homed name resolution,
задуманное сперва, отвергнуто: политика глушит параллельную рассылку, но не откат, и
ключ в реестре переживает падение. NRPT отвергнут тоже: переживает падение, а с
внутренним DNS туннеля после падения у системы не остаётся DNS вовсе.

Сделано фильтрами WFP — тем же способом, что `blockDNS` у wireguard-windows и
`block-outside-dns` у OpenVPN (`winsys.DNSGuard`). Порт 53, UDP и TCP, закрыт ко всем
адресам, кроме DNS туннеля и loopback; процессу `qwdtt-cli` разрешено всё — ядру нужен DNS VK
мимо туннеля (точка 3). Фильтров двенадцать: входящие и исходящие, IPv4 и IPv6, по три.
Сессия WFP динамическая: фильтры снимает система вместе с процессом, и уборка при
запуске не нужна. Открывается она до подключения, чтобы отказ WFP был понятной ошибкой
сразу, а не циклом переподключений; флаг `-allow-dns-leak` разрешает подключиться без
неё (с Э3 — `-allow-leak`, прежнее имя остаётся синонимом). Защита стоит и у `external`:
с `/1` вместо `/0` wireguard-windows свою защиту DNS не включает. На время
переподключения она снимается вместе с маршрутами — иначе DNS туннеля, если он
внутренний, недоступен, а другие запрещены; с kill-switch вместо неё встаёт
«закрыто».

DoH браузеров идёт на порт 443 и фильтром не ловится, но идёт по маршрутам через туннель.

Библиотека — `github.com/tailscale/wf` (BSD-3), подключена через свой форк — почему, см.
«Форки зависимостей» ниже. Запасной путь, если библиотека сломается иначе, — копия пакета
`tunnel/firewall` из wireguard-windows (MIT).

### Kill-switch

Сделан в Э3 (`plan-e3.md`, блоки K и W). У защиты три состояния на весь `qwdtt-cli connect`, и
все — в той же динамической сессии WFP (`winsys.DNSGuard`), что защита DNS:

- **«закрыто»** — с начала `qwdtt-cli connect` до первого подъёма и между попытками
  (`winsys.lockdownRules`, `killswitch_windows.go`). На каждом из слоёв
  `ALE_AUTH_CONNECT` и `ALE_AUTH_RECV_ACCEPT` v4/v6: свой app ID и loopback — вес 15;
  запрет порта 53 — 14 (тяжелее локальной сети: резолвер роутера отдал бы запросы
  провайдеру); DHCP v4/v6, ICMPv6 типов 133–137, локальная сеть (`10/8`, `172.16/12`,
  `192.168/16`, `169.254/16`, `fe80::/10`, `fc00::/7`, мультикаст и широковещание) — 13;
  запрет всего — 12. Правила — по образцу `tunnel/firewall/rules.go` wireguard-windows.
- **«туннель»** — туннель поднят: только защита DNS. Строже не делается: программы с
  привязкой к физическому интерфейсу и внешний адрес корпоративного VPN (маршрут
  конкретнее `/1`) работают как раньше. Поэтому и разрешение интерфейса туннеля по LUID
  не нужно — у `external` он новый на каждую попытку.
- **«окно»** — ручная капча при «закрыто»: правил нет.

Переходы без транзакций WFP: новые правила ставятся от тяжёлых к лёгким, затем старые
снимаются от лёгких к тяжёлым — разрешение `qwdtt-cli` стоит всё время. Не встало новое —
снимаются поставленные новые, прежний набор остаётся. В CLI kill-switch — обёртка
`killSwitchGuard` над защитой: `Disable` у datapath при включённом kill-switch даёт
«закрыто», а не пустую сессию. В `Suspend` и `External.Close` защита переводится
первой, потом снимаются маршруты или служба — без мига без защиты.

**Капча.** Окно WebView2 ходит через локальный прокси `qwdtt-cli` (`captcha/proxy.go`): только
`CONNECT` на 443 к доменам VK (`proxyDomains`), соединения — через хук `netguard` и
резолвер ядра; браузеру он задаётся `--proxy-server` опцией окружения
`AdditionalBrowserArguments` и, для верности, в переменной
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` (одной переменной недостаточно — см. «Форки
зависимостей» ниже).
У окна свой профиль, значит, свой экземпляр `msedgewebview2.exe`. Разрешать `msedgewebview2.exe` по app ID нельзя: им пользуются
Teams, Outlook, виджеты. Kill-switch при этом не снимается. Прокси не поднялся, нет
WebView2 или ручной режим — kill-switch снимается на время капчи, строками «kill-switch
снят на время капчи…» / «kill-switch возвращён…».

**Выключение и отказ.** Поле профиля `kill_switch = false` или флаг `-no-kill-switch`.
Не включился — ошибка до подключения; `-allow-leak` (один на защиту DNS и kill-switch)
разрешает подключиться без него. Отказ «закрыто» посреди сеанса — строка «Внимание:
kill-switch не встал…», попытка не рвётся. Падение `qwdtt-cli` — сессия уходит с процессом,
постоянной блокировки нет (решение 6 Э3).

**Замечено.** `dns = "doh:URL"` с именем хоста из «закрыто» не подключится: загрузочный
резолв DoH ядро делает системным DNS (`doh.go`, `PreferGo: false`), а он закрыт. В README
— задавать адресом; у пресетов первым идёт IP.

### Форки зависимостей

Две библиотеки подключены своими форками через `replace` в `go.mod`. Оба форка — в
организации `FreedomCats`, правка в каждом одна и маленькая, лицензия прежняя. Форк, а не
копия кода в репозиторий: так правка видна одним коммитом поверх апстрима, и её легко
предложить автору или снять, когда апстрим исправится.

**`tailscale/wf` → `FreedomCats/tailscale-wf`** — падение процесса при записи правил WFP.

- *Симптом.* Первый живой подъём `tun` на Windows упал на включении защиты DNS:
  `fatal error: bulkBarrierPreWrite: unaligned arguments` в `wf.toFilter0`
  (`compose.go`). Это `fatal error` рантайма, а не паника: `recover` его не ловит.
- *Причина.* Структуры для вызовов WFP `wf` раскладывает в своей арене (`malloc.go`) —
  память вне кучи Go, выдаваемая сдвигом ровно на запрошенную длину. После блоба нечётной
  длины следующая структура с указателями оказывается невыровненной. Блоб такой длины —
  идентификатор приложения в правиле «свой процесс», его длина зависит от пути к exe.
  Пока GC не размечает кучу, это сходит с рук; если разметка идёт во время записи,
  `typedmemmove` с барьером записи роняет процесс. Ранние прогоны проходили, потому что
  везло со временем GC.
- *Исправление.* `Alloc` округляет длину до выравнивания указателя; тест в самом форке
  (`malloc_test.go`) без правки падает.
- *Регрессия у нас* — `TestDNSGuardUnderGC` (`winsys`, нужны права администратора):
  параллельный `runtime.GC()` и перебор длины app ID от 0 до 7 байт. Без форка падает
  5 прогонов из 5, с форком проходит.
- *Почему форк.* Апстрим `tailscale/wf` не развивается (последний коммит — февраль 2024),
  исправления там нет и ждать его неоткуда.

**`jchv/go-webview2` → `FreedomCats/go-webview2`** — прокси для окна капчи при
kill-switch.

- *Зачем прокси.* При включённом kill-switch («закрыто», §09) окно капчи WebView2 —
  чужой процесс `msedgewebview2.exe` — в сеть не выходит. Ходит оно через локальный прокси
  `qwdtt-cli`, а прокси браузеру задаётся аргументом `--proxy-server`.
- *Симптом.* Тест окна `TestWebView2Proxy` на Windows падал: в прокси не приходило ни
  одного `CONNECT`, в командной строке `msedgewebview2.exe` не было `--proxy-server`.
  Переменную `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` рантайм WebView2 (проверено на
  версии 155, со встроенным в go-webview2 загрузчиком) не применяет вовсе — даже заданную
  до запуска процесса. Читает её сам рантайм, а не загрузчик, так что со стороны
  библиотеки это не исправить. При kill-switch окно капчи из-за этого не загружалось бы.
- *Исправление.* Документированный путь — опция окружения `AdditionalBrowserArguments`
  в `ICoreWebView2EnvironmentOptions`. go-webview2 объекта опций не создаёт и передаёт в
  `CreateCoreWebView2EnvironmentWithOptions` нуль. Форк добавляет в `WebViewOptions` поле
  `AdditionalBrowserArguments` и свой COM-объект опций (`pkg/edge/environmentoptions.go`),
  который `Chromium.Embed` передаёт при создании окружения; тесты COM-объекта — на amd64 и
  386.
- *У нас.* `setBrowserArgs` (`internal/captcha/webview2_windows.go`) собирает итоговую
  строку аргументов; она идёт и опцией, и в переменную окружения — если какой-то рантайм
  переменную применит, по документации она важнее опции. С форком стенд окна зелёный,
  `TestWebView2Proxy` проходит за доли секунды.
- *Почему форк.* Правка — в COM-обвязке библиотеки, снаружи пакета её не сделать: окружение
  создаётся внутри `webview.NewWithOptions` (`Chromium.Embed`), объекта опций туда не
  передать.

### Поставка

Релиз собирает `go run ./scripts/release` (в CI — `release.yml`, с `SHA256SUMS.txt`). Для
Windows — zip: `qwdtt-cli.exe`, `wintun.dll` с её лицензией `wintun-LICENSE.txt`,
`qwdtt-cli.example.toml`, `LICENSE`, `README.md` и `THIRD_PARTY_NOTICES.txt` — лицензии всех
модулей, слинкованных в `qwdtt-cli.exe`, и самого Go (собирает `go run ./scripts/notices`).
Без установщика. Wintun поставляется как
подписанный бинарь от WireGuard LLC; его лицензия допускает распространение
в неизменном виде вместе с программой, которая обращается к DLL только через API
`wintun.h` (так её использует wireguard-go). В репозитории DLL нет: для сборки из
исходников её кладёт `go run ./scripts/wintun`, релиз берёт тем же пакетом
`scripts/internal/wintun` — фиксированная версия, SHA256 архива, на Windows — проверка
подписи DLL.

## 09а. Специфика Linux

Сделано в Э4 (`plan-e4.md`): тот же `tun`, что и на Windows, средствами Linux. Общая
логика datapath, супервизор и `netguard.Guard` не менялись — Linux отдаёт им платформенные
функции.

### Права и запуск

`tun` требует root: адаптер, маршруты, nftables и запись DNS системы. Проверка —
`os.Geteuid() == 0`, без прав — отказ до подключения «запустите qwdtt-cli через sudo».
`setcap` отвергнут: capability слетает при пересборке, а одного `CAP_NET_ADMIN` мало
для `/run/resolvconf` и `/etc/resolv.conf`.

Под `sudo` `qwdtt-cli` работает от имени вызвавшего там, где это касается пользователя
(`internal/sudo`: `SUDO_USER` и его запись в базе пользователей): каталог настроек — его
`~/.config/qwdtt-cli` (`XDG_CONFIG_HOME` root'а не учитывается), созданные файлы и
каталоги — его владельцем (`chown` временного файла до `rename`), браузер капчи
(`xdg-open` и браузер под управлением) — от его имени с его окружением сеанса
(`XDG_RUNTIME_DIR`, шина D-Bus) и в своей группе процессов, чтобы Ctrl+C для `qwdtt-cli` его
не закрыл; временный профиль браузера под управлением — тоже его.

Второй `qwdtt-cli connect -datapath tun` отсекается до подключения абстрактным unix-сокетом
`@qwdtt-cli-tun`: он уходит вместе с процессом, уборка не нужна. Чужой интерфейс с именем
`qwdtt-cli` не удаляется — отказ с подсказкой.

### Адаптер и маршруты

TUN — `tun.CreateTUN` из wireguard-go, настройка — netlink (`vishvananda/netlink`,
`linuxsys`): MTU, адреса `/32` и `/128`, маршруты `0.0.0.0/1`, `128.0.0.0/1`, `::/1`,
`8000::/1` на `qwdtt-cli`. Утилиты `ip` и `nft` не нужны. Интерфейс TUN исчезает вместе с
процессом, маршруты — вместе с интерфейсом: уборки после `kill -9` не нужно (опыт N1).

IPv6 при MTU меньше 1280 ядро на интерфейсе не держит — тогда маршрутов IPv6 на `qwdtt-cli`
нет, а IPv6 системы закрывает таблица защиты DNS (`datapath.IPv6Blocker`); без защиты
(`-allow-dns-leak`) — предупреждение, что IPv6 идёт мимо туннеля.

### DNS системы

Способ выбирается по `/etc/resolv.conf` (`linuxsys.SystemDNS`) и печатается до
подключения:

| `resolv.conf` | Способ | После `kill -9` |
|---|---|---|
| ссылка в `/run/systemd/resolve` или заглушка `127.0.0.53` | systemd-resolved по D-Bus (`godbus/dbus`): `SetLinkDNS`, домен `~.`, `SetLinkDefaultRoute` | уходит вместе с линком |
| ссылка в `/run/resolvconf` или заголовок resolvconf | Debian `resolvconf -a tun.qwdtt-cli` · openresolv `-a tun.qwdtt-cli -m 0 -x` | запись `tun.qwdtt-cli` остаётся |
| обычный файл | перезапись с копией `/etc/resolv.conf.qwdtt-cli-backup` | файл и копия остаются |

Остатки упавшего запуска убирает следующий (`SystemDNS.Recover`) — после `Reserve`,
когда второго `qwdtt-cli` с адаптером быть не может. Ссылка на незнакомый генератор — отказ.
Debian `resolvconf` монопольного режима не умеет: прежние серверы остаются в
`resolv.conf` после туннельных, их закрывает защита DNS. Docker монтирует
`resolv.conf` в контейнер — `rename` поверх даёт `EBUSY`, и тогда файл пишется на месте.

### Защита DNS

Таблица nftables `inet qwdtt-cli` (`google/nftables` из ветки `main`) с флагом `owner`
(ядро 5.12+): ядро удаляет её вместе с netlink-сокетом, который её создал, — то есть с
процессом. Цепочки `output` и `forward` (контейнеры и ВМ за NAT хоста): порт 53, UDP и
TCP, только к DNS туннеля и loopback, сокеты `qwdtt-cli` — по метке `SO_MARK` (под `sudo`
фильтр по uid пропустил бы все процессы root). `drop` в `output` даёт отправителю UDP
`EPERM` сразу, TCP — таймаут. Чужая таблица `inet qwdtt-cli` с владельцем — `EPERM`, а не
`EEXIST`: так узнаётся другой работающий `qwdtt-cli`. На время переподключения правила
снимаются вместе с маршрутами, таблица остаётся; с kill-switch вместо них встаёт
«закрыто» (ниже).

### Что проверено

Живая приёмка — журнал Э4, R2: в контейнере docker (`--cap-add NET_ADMIN`) и на
живой машине. При поднятом туннеле на
физическом интерфейсе к порту 53 — только сокеты ядра к DNS для VK; второй экземпляр —
отказ; `kill -9` — остаётся только DNS системы, его убирает следующий запуск; Ctrl+C —
снимок `checktunnel` совпадает с исходным; обрыв TURN, пропажа и смена сети —
переподключение. Debian `resolvconf` проверен живьём, systemd-resolved и openresolv — в
своих образах docker.

### Kill-switch и поставка

Kill-switch (Э3, блок K) — третий набор правил в той же таблице `inet qwdtt-cli`
(`linuxsys.Lockdown`, `killswitch_linux.go`), состояния те же, что на Windows (§09).
«Закрыто»: в `output` — разрешены метка `qwdtt-cli` и `lo`, затем запрет порта 53, затем
разрешены DHCP v4/v6, ICMPv6 ND/RA, локальная сеть, мультикаст и широковещание, в конце
`drop`; в `forward` — то же без метки, loopback и служебных протоколов, так что
контейнеры и ВМ тоже закрыты. `drop` нашей цепочки
окончателен поверх `accept` чужих таблиц (docker, firewalld). Переход — одним пакетом
netlink (`FlushTable` + правила + `Flush`). Метка `SO_MARK` у сокетов ядра ставится, когда
открыта таблица защиты DNS — kill-switch без неё не бывает. Ручная капча в браузере
пользователя — «окно» (правил нет): разрешить браузер отдельно нечем. Проверено живьём в
контейнере и на машине (`plan-e3.md`, K5). Браузер под управлением правил не снимает: он
ходит через прокси капчи на `lo`, а прокси — сокетами `qwdtt-cli` с меткой, как окно WebView2
на Windows (§09).

Поставка — `qwdtt-cli_<версия>_linux_amd64.tar.gz` из `go run ./scripts/release`: каталог со
статическим `qwdtt-cli` (`CGO_ENABLED=0`, без glibc, 0755), `LICENSE`,
`THIRD_PARTY_NOTICES.txt`, `README.md`, `qwdtt-cli.example.toml`. Архив пишет сам скрипт, а не
`tar` системы, в формате ustar с фиксированным временем записей — права на исполнение не
зависят от системы сборки, время файлов машины сборки в архив не попадает, и одинаковые
файлы дают одинаковый архив (решение R3).

## 10. Конфиг и секреты

```toml
# %APPDATA%\qwdtt-cli\profiles.toml

default_profile = "home"

[profile.home]
peer           = "203.0.113.10:56000"
password_ref   = "dpapi:8f2a…"   # пароль подключения = WRAP-ключ
vk_hashes_ref  = "dpapi:1c9b…"
workers        = 18              # кратно 9; максимум 108
obfs           = "audio"         # audio | video
turn_transport = "udp"           # udp | tcp — tcp против душения UDP
dtls           = false           # false = прямой RTP-obfs AEAD
dns            = "doh-yandex"    # резолвер для доменов VK
datapath       = "tun"           # tun (прежнее имя wintun) | socks | external

[profile.home.socks]
listen = "127.0.0.1:1080"
```

В TOML не лежит ни одного секрета. Пароль и хеши хранятся зашифрованными через DPAPI и
привязаны к учётной записи Windows — файл, скопированный на другую машину, бесполезен.
Записываются командой `qwdtt-cli profile set`, которая читает значение из скрытого ввода,
а не из аргумента командной строки, чтобы секрет не попал в историю оболочки.
На Linux и macOS секреты лежат в `secrets.json` без шифрования, под правами `0600`;
связка ключей — задача «Вне этапов» ниже. Под `sudo` это файлы вызвавшего (§09а).

Число воркеров нормализуется по правилам ядра: группа — девять воркеров (`group.go:14`),
значение округляется вниз до кратного девяти, потолок 108. В режиме авторизации по аккаунту
VK потолок опускается до четырёх — такова квота TURN на сессию.

Что из этого сделано в Э1 (задача C1):

- умолчания берутся из `core.DefaultConfig`; `datapath` в настройки ядра не попадает
  вовсе — с D2 ядро о способе доставки не знает, а умолчание (в Э1 — `socks`, с
  Э5 по решению 5 — `tun`, на macOS — `socks`; `config.EffectiveDatapath`)
  и секцию `[profile.<имя>.socks]` читает CLI и отдаёт конструктору из `internal/datapath`;
- `datapath = "tun"` (тогда — `wintun`) в Э1 отвергался с объяснением; принимается
  с Э2, на Linux — с Э4;
- неизвестный ключ — ошибка, а не мусор: опечатка в имени означает, что настройка
  не применилась, и заметить это иначе было бы можно только по странному поведению.
  Отдельно ловятся `password` и `vk_hashes`: человек пытался положить секрет в файл,
  и ему нужно сказать, куда тот кладётся на самом деле;
- пропущенное `dtls` и `dtls = false` — разные вещи, поэтому поле разбирается
  в указатель: прямой режим без DTLS требует сервера с `-listen-direct`,
  включать его молча нельзя.

Что добавила задача C3 (`qwdtt-cli profile`):

- файл записывается целиком и из структуры, а не правится построчно: разбор
  отдаёт структуру, а не дерево с комментариями. Комментарии пользователя при
  `qwdtt-cli profile set` теряются — предупреждение стоит в шапке записанного файла;
- пустые поля не записываются вовсе. Пропуск означает «как по умолчанию», и
  вписать вместо него нынешнее умолчание значило бы заморозить его в чужом файле:
  смена умолчания в новой версии до такого профиля уже не дошла бы;
- секреты каждого профиля лежат под именами `<профиль>.password` и
  `<профиль>.vk_hashes`, поэтому `qwdtt-cli profile rm` знает, что удалять, а повторный
  `set` перезаписывает запись, а не заводит новую.

### Вне этапов. Служебные скрипты на Go — около дня · сделано

Решение пользователя: скрипты в `scripts/` переводятся с PowerShell на Go.
Go у собирающего есть всегда, а `pwsh` на Linux и macOS ставится отдельно. Python
отвергнут по той же причине — лишняя зависимость сборки. Новые скрипты сразу пишутся
на Go (пакет `main` в `scripts/<имя>/`, тесты — обычным `go test`); первый такой —
`scripts/notices` (R1 этапа Э2).

Что перевести:

- `build-release.ps1` (≈200 строк) → `scripts/release`: `go build` по платформам
  с `-trimpath` и `ldflags` версии, zip через `archive/zip`, вызов `notices`,
  проверка `qwdtt-cli version` у бинаря своей платформы.
- `fetch-wintun.ps1` (≈120) → `scripts/wintun` или часть `release`: скачивание,
  SHA256 зашитого архива, распаковка DLL и её лицензии. Подпись Authenticode —
  `WinVerifyTrust` через `x/sys/windows` только на Windows; на других ОС остаётся
  проверка хеша (он зашит, подпись — второй рубеж).
- `send-ctrl-break.ps1` (≈50) → `scripts/ctrlbreak` с `//go:build windows`:
  `FreeConsole`, `AttachConsole`, `SetConsoleCtrlHandler`, `GenerateConsoleCtrlEvent`.
- `vendor-core.ps1` (≈670) → `scripts/vendorcore`: правила правок апстрима (Р7).
  Самый объёмный и самый чувствительный.

**Готово когда:** в `scripts/` нет `.ps1`. `vendorcore` на том же коммите qWDTT
даёт `internal/core`, побайтово совпадающий с результатом старого скрипта. `release`
из чистого клона на Windows и на Linux даёт zip с одинаковым набором файлов, а
`qwdtt-cli.exe` той же версии — с тем же хешем. README, этот документ и планы ссылаются на
новые команды.

**Когда:** только на Windows: новые версии должны работать полностью идентично старым,
а сравнить их можно, лишь запустив старые (решение пользователя). Поэтому
Linux-часть Э4 идёт раньше этой задачи, а релиз до перевода собирается на Windows
старым `build-release.ps1`.

**Состояние (коммит 1ad0ae4).** Сделано на Linux по просьбе пользователя
(«весь PowerShell — на Go или Python, работать идентично»): сравнение со старыми
скриптами — в контейнере `qwdtt-pwsh` (pwsh 7.4) с Go хоста. В `scripts/` нет `.ps1`;
шаги release.yml на PowerShell тоже переведены (`distcheck`, `sha256sums`), шаги — в bash.

- `vendorcore`: на апстриме `fae121e` и на испорченных деревьях (удалённый, лишний,

- `wintun`: файлы и время из архива те же; подписант из PKCS#7 разобран на настоящей

### Вне этапов. Секреты в связке ключей на Linux и macOS — полдня–день · Linux сделан

Вопрос пользователя: почему на Linux и macOS секреты не шифруются, если
есть Secret Service (libsecret, `secret-tool`) и связки ключей. Решение — записать
задачей.

**Как сейчас.** На Windows пароль и хеши шифрует DPAPI (схема ссылки `dpapi:`). На
прочих системах `protect`/`unprotect` — тождество, защищают только права `0600` на
`secrets.json` (схема `file:`, `secret_unix.go`). Так решено в Э1 (задача C2): своё
шифрование с ключом в том же каталоге было бы самообманом, а настоящую связку отложили
до Э4.

**Что даст.** То же, что DPAPI: секреты зашифрованы на диске, и копия каталога
настроек, бэкап или синхронизация их не выдают. От чужого процесса того же
пользователя не защищает — Secret Service отдаёт секреты любому процессу сессии, как
DPAPI.

**Что сделать.**

- Linux — Secret Service по D-Bus на чистом Go (`github.com/godbus/dbus`, новая
  зависимость: в `go.sum` её пока нет). libsecret требует cgo, а сборка идёт с
  `CGO_ENABLED=0`; `secret-tool` — подпроцесс, годится как запасной путь, но хрупок.
  Схема ссылки — своя (например, `secretservice:`), чтобы ссылка одного хранилища
  не разворачивалась другим, как сейчас `dpapi:` и `file:`.
- macOS — Keychain. Без cgo — только утилита `security`, секрет передавать через
  stdin, не аргументом.
- Сервиса нет (SSH, сервер, минимальная сессия) — остаётся файл `0600`, и `qwdtt-cli profile
  set` / `show` говорят, какое хранилище выбрано (`secretStoreKind`). Переезд уже
  записанных `file:`-секретов в связку — по `qwdtt-cli profile set`, не молча.
- Заблокированная связка вызывает графический диалог разблокировки. Для консольного
  клиента это то же, что `CRYPTPROTECT_UI_FORBIDDEN` у DPAPI: решить, разрешать ли
  диалог или отказывать с понятной ошибкой.
- Провайдеров Secret Service на машине бывает несколько (`gnome-keyring-daemon`, KeePassXC,
  KWallet) — проверить, кто владеет `org.freedesktop.secrets`, и работу с разными.

**Открыто для Э4 — права.** Полному туннелю на Linux нужны права. `sudo qwdtt-cli connect`
работает от root, а у root нет сессии D-Bus пользователя и его связки — секреты не
прочитать (на Windows такой проблемы нет: консоль администратора — та же учётная
запись). Варианты — `CAP_NET_ADMIN` бинарю через `setcap`, и `qwdtt-cli` работает от
пользователя, или отдельный процесс с правами только для туннеля. От этого выбора
зависит, будет ли связка полезна для режима полного туннеля; решается в Э4, но
до реализации этой задачи стоит его учесть.

**Готово когда:** на Linux с Secret Service `qwdtt-cli profile set` кладёт секреты в связку,
в `secrets.json` их нет, `qwdtt-cli connect` их читает, `qwdtt-cli profile rm` удаляет; без сервиса —
файл `0600` и строка о том, какое хранилище выбрано; тесты хранилища — с подделкой
сервиса D-Bus. macOS — тем же интерфейсом, проверка — когда будет машина.

**Когда:** к этапам не привязано; Linux проверяется на машине разработки. Разумно
не позже Э4.

**Состояние (коммит daf96d0) — Linux сделан.** Решения пользователя: переносить
только новые и перезаписанные секреты (без автопереноса и отдельной команды); заблокированная связка — показывать окно разблокировки; утилита должна
работать и без графики — тогда файл. Сделано: пакет `internal/secretservice` (godbus, алгоритм
`plain`, коллекция по умолчанию, только уже запущенный сервис — без D-Bus activation, окно
разблокировки с пределом 2 мин); ссылка `secretservice:<id>`, в `secrets.json` — запись с
`store: secretservice` без данных; `file:` читается как прежде. **Права:** root к шине
пользователя `dbus-daemon` не пускает (проверено), поэтому под sudo — скрытая команда
`__secret-service`, запуск себя от имени вызвавшего (`sudo.SessionEnv`, вынесен из captcha),
JSON через stdin/stdout. Проверено живьём: `profile set` → записи в связке, `show` без и под sudo, `set
-password` под sudo, `rm` — связка чистая; профиль с `file:` читается. Не проверено живьём:
окно разблокировки (проверено тестами на поддельном сервисе) и
KeePassXC в роли владельца имени. macOS (Keychain) — когда будет машина.

### Вне этапов. Капча в браузере под управлением (CDP) на Linux — 1,5–2 дня · сделано

Решено ещё в Э1 (`e2-captcha.md`, §4 и §8: «CDP — к Э4»), но в план Э4 не попало. Записано
заново по решению пользователя.

> **Состояние — сделано.** Решатель `captcha.Browser` (`internal/captcha/browser_linux.go`),
> протокол — `cdp.go`, заглушка вне Linux — `browser_other.go`. Отличия от постановки ниже:
>
> - **Транспорт — труба, а не порт** (решение пользователя): `--remote-debugging-pipe`,
>   команды браузер читает из дескриптора 3, ответы пишет в 4 (`exec.Cmd.ExtraFiles`),
>   сообщения — JSON с нулевым байтом в конце. Ни WebSocket, ни новых зависимостей; чужой
>   процесс к браузеру не подключится; файл `DevToolsActivePort` читать не нужно — у
>   Chromium из snap свой `/tmp`. Работает и через скрипт-обёртку, которой дистрибутивы
>   запускают Chromium. Цена — только Linux: на Windows `ExtraFiles` нет, там окно WebView2
>   или ручной режим.
> - **`navigator.webdriver`.** В современном Chromium его выставляет любое управление по
>   DevTools — и труба, и порт, — а не только `--enable-automation`. Снимает признак
>   `--disable-blink-features=AutomationControlled` (`Emulation.setAutomationOverride` умеет
>   его только включить); плашку «неподдерживаемый флаг командной строки», которую Chromium
>   на него показывает, убирает `--test-type`, как у ChromeDriver. Стенд проверяет, что
>   странице видно `false`.
> - **Вкладка — та, с которой браузер запустился** (`about:blank`), а не вторая рядом:
>   `Target.getTargets` → `attachToTarget` (flatten) → `Network.enable`,
>   `Target.setAutoAttach` (фреймы других сайтов и воркеры — свои процессы, их запросы вкладке
>   не видны) → `Page.navigate`. Слайдер окно не закрывает; preflight и ответы без токена
>   пропускаются, как в перехватчике JS.
> - **Браузер не запустился** (`captcha.ErrBrowser`: процесс вышел, страница не открылась за
>   20 с) — та же капча уходит в ручной режим (`fallbackCaptcha` в `internal/cli/connect.go`).
>   Нет браузера на Chromium — ручной режим с подсказкой, какой браузер поставить; без
>   предупреждения при запуске.
> - Выбор в `captchaSolver`: WebView2 → браузер → ручной; при kill-switch оба окна — через
>   прокси (`proxiedSolver`), без прокси — запасное со снятием kill-switch.
> - Временные профили обоих окон — общий `profile.go`.
>
> Проверено: автомат CDP — тестами на записанных сообщениях (`cdp_test.go`, на любой ОС);
> живой стенд `QWDTT_BROWSER=1 go test ./internal/captcha -run Browser` на Chromium — fetch,
> XHR, фрейм другого сайта, слайдер, отказ VK, `navigator.webdriver`, закрытие окна, срок,
> сбой запуска, прокси с TLS-стендом, путь через диспетчер; под `sudo` — браузер от имени
> пользователя, профиль убран. **Не проверено живьём:** капча настоящей VK и `connect` с
> kill-switch на машине — по случаю, когда VK попросит капчу.

**Как сейчас.** На Linux (и на Windows без WebView2 Runtime) шаг 4 капчи — ручной режим
(§08): браузер открывается сам, но токен человек достаёт из консоли браузера однострочником и
вставляет в терминал. Это пять действий под таймером, одно из них — F12. И на время ручной
капчи снимается kill-switch: браузер пользователя — чужой процесс, пропустить мимо блокировки
только его нечем (§09а).

**Что сделать.** `qwdtt-cli` сам запускает установленный браузер на Chromium (Chrome,
Chromium, Edge, Яндекс Браузер, Brave, …) со своим временным профилем и
`--remote-debugging-port=0`, открывает страницу капчи и забирает токен по протоколу DevTools:
`Network.responseReceived` для `captchaNotRobot.check` → `Network.loadingFinished` →
`Network.getResponseBody` → `successTokenFrom` (`internal/captcha/token.go`). Человек только
решает капчу — как в окне WebView2. Поток по шагам, поиск браузера, безопасность порта —
`e2-captcha.md`, §4.

- **Kill-switch остаётся включённым.** Запущенному браузеру задаётся `--proxy-server` на
  локальный прокси капчи (`internal/captcha/proxy.go`, кроссплатформенный): только `CONNECT`
  к доменам VK через `netguard`, как у окна WebView2 (§09). Свой экземпляр со своим профилем —
  значит, другие окна браузера пользователя через прокси не пойдут.
- **Под `sudo`** браузер запускается от имени вызвавшего пользователя, с его окружением сеанса
  (`sudo.SessionEnv`, как `xdg-open` сейчас), временный профиль — в его каталоге.
- **Без cgo**: только `os/exec`, HTTP и WebSocket. Транспорт WebSocket — открытый вопрос
  (`e2-captcha.md`, §4: `bogdanfinn/websocket` из графа модулей, свой минимальный клиент или
  новая зависимость вроде `coder/websocket`) — решить с пользователем.
- **Нет браузера на Chromium** (только Firefox) или он не стартовал — откат на нынешний ручной
  режим, как у WebView2 без Runtime. Firefox по CDP больше не управляется; WebDriver BiDi —
  отдельная задача, если понадобится.
- Решатель — `captcha.Solver` с `NeedsHuman() == true`, выбор в `captchaSolver`
  (`internal/cli/connect.go`): WebView2 → CDP → ручной. На Windows CDP — запасной путь,
  когда нет WebView2 Runtime (Edge есть всегда).
- Не запускать браузер с `--enable-automation` и `--headless`: первый выставляет
  `navigator.webdriver`, второй человеку не покажет окно.

**Почему не встроенный движок.** WebKitGTK, Qt WebEngine и CEF подключаются только через cgo и
системные библиотеки: пропали бы статический бинарь без glibc (§09а), кросс-сборка релиза и
независимость от версии дистрибутива; CEF добавил бы к бинарю 100+ МБ.

**Готово когда:** на Linux с Chromium-браузером капча из ручного режима решается без
консоли браузера и без вставки токена; при kill-switch он не снимается, наружу ходит только
прокси капчи; под `sudo` браузер — пользовательский; без браузера — ручной режим; тесты
разбора событий CDP — на записанных ответах, запуск браузера — по флагу на машине с
браузером. README («Быстрый старт», «Kill-switch») — по новому поведению.
