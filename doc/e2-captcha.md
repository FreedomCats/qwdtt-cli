# Четвёртый шаг капчи: чем заменить «вставьте URL редиректа»

Рабочий документ к задаче E2. Написан после того, как разведка в E1 показала, что
первоначальная формулировка задачи опирается на неверную предпосылку.

Здесь разобраны два пути, которые пользователь просил проработать: **браузер под
управлением** (вариант 2) и **окно WebView2** (вариант 3). Третий, консольный, оставлен
как опорная точка сравнения — без него не обойтись в любом случае.

---

## 1. Что выяснено

Все утверждения ниже проверены по коду, ссылки — на файлы в репозиториях на диске.

**Токена в адресной строке не существует.** Страница капчи после решения никуда не
переходит со значением в URL. Токен — это поле `success_token` в **теле** JSON-ответа VK
на запрос `captchaNotRobot.check`. Android доставал его инъекцией JS, подменяя `fetch`
и `XMLHttpRequest.prototype.send`:

- `app/src/main/java/com/wdtt/client/vk/CaptchaWebViewManager.kt:70–125` — автоматический шаг;
- `.../ManlCaptchaWebViewManager.kt:150–200` — ручной шаг, тот же перехватчик;
- мост в Go/Kotlin: `addJavascriptInterface(…, "WdttCaptcha")`, метод `onSuccess(token)`.

Перехватчик различает три исхода: `response.success_token` — успех,
`response.show_captcha_type == "slider"` — попался слайдер, `data.error` — отказ VK.

**Токен переносим между клиентами.** Это главный вывод для обоих вариантов, и он
подтверждается с двух сторон:

- Android перед показом WebView **чистит** cookies VK (`VkWebViewCookies.kt`) и ставит
  **случайный** desktop-Chrome UA (`VkCaptchaWebViewUa.kt`). Ни cookies, ни UA, ни
  TLS-отпечаток с Go-клиентом не делятся;
- нативный решатель ядра шлёт в `captchaNotRobot.check` выдуманный `browser_fp`, новый на
  каждую попытку (`internal/core/captcha_v2.go:319`, `rotateCaptchaV2Identity`).

То есть VK связывает `success_token` только с сессией капчи — `session_token` из
`redirect_uri` — и не проверяет, кто именно её решил. Значит, капчу законно решать в
постороннем браузере, а токен предъявлять ядром.

**Что ядро делает с токеном.** `internal/core/creds.go:518`: повторяет
`calls.getAnonymousToken`, добавив `captcha_sid`, `captcha_ts`, `captcha_attempt`
и `success_token`. Капчу ядро терпит трижды за попытку получения кредов; после третьего
раза ставит `globalCaptchaLockout` на 60 секунд (`creds.go:494`).

**Окно ожидания — 60 секунд.** `captchaManualWebViewTimeout` (`internal/core/creds.go:217`),
та же величина, что `CAPTCHA_TIMEOUT_MS` в `ManlCaptchaWebViewManager.kt:37`. На Android
за эту минуту пользователь успевал, потому что окно всплывало само. У нас на неё же
ложится запуск браузера.

**По плану это Э2.** `architecture.md` §11: в Э1 «нативный решатель плюс ручной режим»,
капча через WebView2 отнесена к Э2. Оба разбираемых варианта — это перенос работы из Э2
в Э1, и решать, стоит ли, нужно явно.

## 2. Что от решателя требует каркас E1

Контракт уже зафиксирован в `internal/captcha/solver.go`:

```go
type Solver interface {
	Solve(ctx context.Context, req Request) (string, error)
	NeedsHuman() bool
}
```

- `req.RedirectURI` — страница капчи, `req.SessionToken` — сессия, `req.Deadline` — момент,
  после которого ответ бесполезен (окно ядра минус запас в секунду).
- `Solve` обязан вернуться по `ctx.Done()`: ctx несёт и срок, и Ctrl+C.
- Ошибка и пустой токен читаются одинаково — «не решил»; диспетчер сам отправит ядру отказ.
- Отвечать ядру решателю не нужно, `SubmitCaptcha` зовёт диспетчер.
- `NeedsHuman() == true` означает, что на десятисекундные окна `WBV Auto` решатель звать
  не будут: диспетчер откажется за него сразу.

Обоим вариантам этого контракта достаточно. Ни один не требует правок в E1.

## 3. Вариант 3 — окно WebView2 (только Windows)

Точный перенос того, что делает Android: своё окно, свой движок, тот же перехватчик JS.

### Механизм

Библиотека — `github.com/jchv/go-webview2`. Проверено по модулю
`v0.0.0-20260205173254-56598839c808`, скачанному в кеш:

| Свойство | Значение |
|---|---|
| Лицензия | MIT — с GPL v3 совместима |
| cgo | **не нужен**: `import "C"` в модуле не встречается ни разу |
| Зависимости | `github.com/jchv/go-winloader` и `golang.org/x/sys` (последний у нас уже прямой) |
| Загрузчик | `WebView2Loader.dll` встроен в модуль и грузится из памяти (`webviewloader/module.go`, `loadFromMemory`) — класть файл рядом с бинарём не нужно |
| Проверка среды | `webviewloader.GetInstalledVersion()` — ровно то, чем определяется «WebView2 Runtime не найден» |

Отсутствие cgo — решающее: критерий A3 требует кросс-сборок с `CGO_ENABLED=0`, и
зависимость с cgo сломала бы их даже под Windows.

Нужные методы интерфейса `webview.WebView`:

- `Init(js)` — код выполняется **до** `window.onload` на каждой новой странице. Это строже,
  чем у Android, где инъекция шла по `onPageStarted`/`onPageFinished` и теоретически могла
  опоздать за быстрым XHR;
- `Bind(name, fn)` — глобальная JS-функция, зовущая Go. Замена `addJavascriptInterface`;
- `Navigate(url)`, `Run()` (блокирует до конца), `Terminate()` — и он **безопасен из чужой
  горутины**, что и нужно для `ctx.Done()`;
- `WebViewOptions.DataPath` — каталог профиля. Свой временный каталог заменяет
  `clearCaptchaCookies()` Android: чистая сессия по построению.

### Устройство решателя

```go
//go:build windows

type WebView2 struct{ opts WebView2Options }

func NewWebView2(opts WebView2Options) (*WebView2, error) {
	if _, err := webviewloader.GetInstalledVersion(); err != nil {
		return nil, fmt.Errorf("WebView2 Runtime не найден: %w", err)
	}
	return &WebView2{opts: opts}, nil
}

func (*WebView2) NeedsHuman() bool { return true }

func (s *WebView2) Solve(ctx context.Context, req captcha.Request) (string, error) {
	result := make(chan string, 1)
	failure := make(chan error, 1)

	profile, cleanup, err := tempProfile()   // каталог WebView2, удаляется в конце
	if err != nil {
		return "", err
	}
	defer cleanup()

	done := make(chan struct{})
	go func() {
		// Окно и насос сообщений живут на одной прибитой нити: Dispatch шлёт
		// PostThreadMessage именно тому потоку, который создал окно.
		runtime.LockOSThread()
		defer runtime.UnlockOSThread()
		defer close(done)

		w := webview.NewWithOptions(webview.WebViewOptions{
			DataPath:      profile,
			WindowOptions: webview.WindowOptions{Title: "Капча VK", Width: 460, Height: 600, Center: true},
		})
		defer w.Destroy()

		_ = w.Bind("__qwdttCliCaptchaSuccess", func(token string) {
			select { case result <- token: default: }
			w.Terminate()
		})
		_ = w.Bind("__qwdttCliCaptchaFailed", func(reason string) {
			select { case failure <- errors.New(reason): default: }
			w.Terminate()
		})
		w.Init(interceptorJS)      // тот же перехватчик, что у Android
		w.Navigate(req.RedirectURI)
		w.Run()                    // выходит по Terminate или по закрытию окна
	}()

	stop := context.AfterFunc(ctx, func() { /* Terminate через сохранённую ручку */ })
	defer stop()

	select {
	case token := <-result:
		return token, nil
	case err := <-failure:
		return "", err
	case <-done:
		// Окно закрылось, а токена нет — пользователь передумал.
		return "", errors.New("окно капчи закрыто")
	case <-ctx.Done():
		<-done
		return "", ctx.Err()
	}
}
```

Перехватчик — константа, общая с вариантом 2 (разница только в том, как вызвать Go:
`window.__qwdttCliCaptchaSuccess(token)` вместо `window.WdttCaptcha.onSuccess(token)`).

> **Поправки к эскизу — сделано в E3.** Решатель написан по этому эскизу,
> но четыре места в нём неверны, проверено по коду библиотеки и прогоном:
>
> - `Terminate()` — это `PostQuitMessage`, выход для очереди **вызывающей** нити. Из чужой
>   горутины он окно не закрывает. Закрывать нужно через `Destroy()`: это
>   `PostMessage(WM_CLOSE)` самому окну, его можно звать с любой нити, и дальше окно
>   выходит из `Run()` тем же путём, что по крестику.
> - `GetInstalledVersion()` без Runtime возвращает пустую версию **без ошибки** — проверять
>   нужно версию, а не только `err`.
> - COM библиотека инициализирует в `init()` пакета, то есть на случайной нити. На своей
>   прибитой нити решатель зовёт `CoInitializeEx(COINIT_APARTMENTTHREADED)` сам.
> - Привязка одна, `__qwdttCliCaptchaResult(kind, value)`, а не две: так устроен перехватчик
>   в `token.go`. `"slider"` окно не закрывает — человек решит и слайдер, а ручное окно
>   Android слайдер не ловило вовсе.

### Что придётся учесть

- **Ручка `w` нужна снаружи горутины**, чтобы звать `Terminate()` по `ctx.Done()`. Проще
  всего положить её в поле под мьютексом и обнулять после `Run()`.
- **Временный профиль не удаляется сразу.** Процесс `msedgewebview2.exe` держит файлы
  каталога ещё какое-то время после `Destroy()`. `os.RemoveAll` в этот момент вернёт
  «файл занят» — нужен цикл с несколькими попытками, а при неудаче каталог стоит просто
  оставить в `%TEMP%` и не считать это ошибкой: секретов в нём нет.
- **User-Agent не переопределить через верхний интерфейс.** `PutUserAgent` существует
  (`pkg/edge/ICoreWebViewSettings.go:302`), но поле `browser` в структуре `webview`
  неэкспортируемое, и `GetSettings()` снаружи не достать. Обойти можно, собрав окно на
  `pkg/edge.Chromium` вручную. **Рекомендация: не трогать.** Случайный UA на Android нужен
  был автоматическому шагу, где попыток много и они похожи друг на друга; здесь капчу
  решает человек в честном Edge, и подменять UA не за чем. Если VK всё же начнёт выдавать
  слайдер чаще обычного — вот запасной выход.
- **Консольное приложение открывает окно** — на Windows это законно, консоль остаётся.

### Итого по варианту 3

| | |
|---|---|
| Платформы | Только Windows (для Э1 это и есть целевая платформа) |
| Новые зависимости | 2 модуля, MIT, без cgo, ~1.5 МБ в бинаре |
| Требования к среде | WebView2 Runtime; есть в Windows 11 и в актуальных Windows 10, но не гарантирован |
| Деградация | Runtime нет → `NewWebView2` вернёт ошибку, и CLI подставит консольный решатель |
| Укладывается в 60 с | Да: окно поднимается за секунду-полторы |
| Объём работ | **0.5–1 день** вместе с тестами |
| Риск | Низкий: это ровно то, что работает в проде на Android |

## 4. Вариант 2 — браузер под управлением (CDP)

Поднять обычный Chromium с отладочным портом, показать пользователю страницу капчи
и снять токен из сетевого ответа.

### Что важно знать заранее

**Подключиться к уже открытому браузеру пользователя нельзя.** `--remote-debugging-port`
задаётся только при запуске. Вдобавок Chrome с версии 136 игнорирует этот флаг, если
профиль — стандартный. Значит, в любом случае мы **запускаем свой** экземпляр с временным
профилем; это не ограничение, а скорее удобство — чистая сессия, как `clearCaptchaCookies`
у Android.

**Перехватывать можно на сетевом уровне, не трогая страницу.** Это единственное реальное
преимущество варианта перед WebView2. У WebView2 доступа к телу ответа нет
(`ICoreWebView2_2.WebResourceResponseReceived` библиотекой не обёрнут), и остаётся
подмена `fetch` — а подменённый `fetch` антибот-система в принципе умеет замечать. CDP
даёт тело ответа снаружи страницы: `Network.responseReceived` → `Network.loadingFinished`
→ `Network.getResponseBody`. Страница при этом не изменена ни на байт.

**`navigator.webdriver` при этом остаётся `false`.** Его выставляет `--enable-automation`
(им пользуется ChromeDriver), а не сам по себе отладочный порт. Запускать нужно без него.

> **Поправка — при реализации.** Неверно: в современном Chromium `navigator.webdriver` выставляет
> любое управление по DevTools — и `--remote-debugging-port`, и `--remote-debugging-pipe`.
> Признак снимает `--disable-blink-features=AutomationControlled`, а плашку о
> неподдерживаемом флаге, которую Chromium на него показывает, — `--test-type`.

### Поток работы

```
1. Найти браузер
   Windows: msedge.exe в %ProgramFiles(x86)%\Microsoft\Edge\Application (есть всегда),
            chrome.exe через HKLM\...\App Paths\chrome.exe
   Linux:   google-chrome / chromium / chromium-browser / microsoft-edge в PATH
   macOS:   /Applications/{Google Chrome,Microsoft Edge,Chromium}.app/Contents/MacOS/…

2. Запустить
   --remote-debugging-port=0        порт выберет система
   --user-data-dir=<временный>      обязателен, см. выше
   --no-first-run --no-default-browser-check --no-service-autorun
   about:blank                      целевую страницу откроем сами, через CDP
   (без --enable-automation и без --headless)

3. Узнать порт
   <user-data-dir>/DevToolsActivePort — первая строка. Файл появляется не мгновенно,
   нужен короткий опрос с отменой по ctx.

4. Подключиться
   GET http://127.0.0.1:<порт>/json/version → поле webSocketDebuggerUrl
   WebSocket без заголовка Origin (Chrome 111+ иначе откажет)

5. Открыть вкладку и подписаться
   Target.createTarget {url: req.RedirectURI}  → targetId
   Target.attachToTarget {targetId, flatten: true} → sessionId
   Network.enable (в этой сессии)

6. Снять токен
   Network.responseReceived, url содержит "captchaNotRobot.check" → запомнить requestId
   Network.loadingFinished с этим requestId → Network.getResponseBody
   → JSON → response.success_token

7. Убрать за собой
   Browser.close, дождаться выхода процесса, убить по таймауту, удалить временный профиль
```

Пункт 6 — единственное место, где вариант принципиально отличается от Android. Остальное
— обвязка.

### Устройство решателя

```go
type Browser struct{ opts BrowserOptions }

func NewBrowser(opts BrowserOptions) (*Browser, error) {
	exe, err := findChromium(opts.Path)   // ошибка, если браузера нет вовсе
	...
}

func (*Browser) NeedsHuman() bool { return true }

func (b *Browser) Solve(ctx context.Context, req captcha.Request) (string, error)
```

`Solve` держит одну вкладку и одно WebSocket-соединение, и завершается по первому из
четырёх событий: токен получен, VK вернул ошибку, пользователь закрыл окно
(`Target.targetDestroyed` или выход процесса), `ctx` отменён. Закрытие окна нужно ловить
отдельно: иначе передумавший пользователь заставит ядро выстоять весь таймаут вместо того,
чтобы сразу пойти дальше.

### Транспорт WebSocket: три пути, все с изъяном

CDP — это JSON-RPC поверх WebSocket, и клиента у нас нет.

1. **`github.com/bogdanfinn/websocket`** уже в графе модулей (косвенная, через tls-client)
   и это форк gorilla/websocket. Ничего добавлять не нужно. Изъян: форк принадлежит
   tls-client и импортирует `bogdanfinn/fhttp` вместо `net/http` — мы бы привязали работу
   капчи к зависимости ядра, с которой она никак не связана. Уйдёт tls-client — сломается
   капча.
2. **Свой минимальный клиент**, ~150 строк: рукопожатие обычным `net/http`, маскирование,
   текстовые кадры, длины 16/64 бита. Фрагментацию и сжатие Chrome не требует. Изъян —
   свой код в месте, где ошибиться легко и незаметно.
3. **Новая зависимость** вроде `github.com/coder/websocket` — без транзитивных
   зависимостей. Изъян: ещё один модуль в проекте; лицензию нужно сверить с GPL v3.

Отдельно: у Chrome есть транспорт «CDP по трубе» (`--remote-debugging-pipe`), который
обошёлся бы без WebSocket и не открывал бы локальный порт. Он требует передать процессу
унаследованные дескрипторы, а `exec.Cmd.ExtraFiles` на Windows не поддерживается — путь
закрыт.

> **Выбрано — труба.** Задача делалась для Linux, где `ExtraFiles` есть, а на Windows
> окно капчи даёт WebView2. Труба закрывает и вопрос транспорта, и вопрос безопасности
> порта (ниже): порта нет. Устройство — `architecture.md` §11, «Капча в браузере под
> управлением (CDP) на Linux».

### Безопасность

Отладочный порт на `127.0.0.1` принимает соединения от любого процесса пользователя,
и подключившийся получает полный контроль над этим экземпляром браузера. Смягчает
положение то, что экземпляр временный и пустой: ни истории, ни паролей, ни cookies —
только страница капчи. Порт живёт секунды и закрывается вместе с процессом. Отмечать
в документации стоит, но запретом это не является.

|---|---|

| Новые зависимости | Одна (клиент WebSocket) либо свой код |
| Требования к среде | Установленный Chromium: Edge на Windows есть всегда, на Linux/macOS — как повезёт |
| Деградация | Браузера нет → `NewBrowser` вернёт ошибку, CLI подставит консольный решатель |

| Риск | Средний: много движущихся частей — поиск браузера, файл порта, WS, жизненный цикл процесса |

## 5. Опорная точка: консольный вариант

Ради честного сравнения. Печатаем ссылку, пользователь решает капчу в своём браузере,
после чего **сам достаёт токен**. В лоб это «откройте DevTools → Network → найдите
`captchaNotRobot.check` → скопируйте `success_token`» — инструкция для разработчика.

Смягчить её можно так: печатать вместе со ссылкой однострочник для консоли браузера,
который ставит тот же перехватчик и выводит токен готовым к копированию. Тогда от
пользователя нужно: открыть ссылку, нажать F12, вставить строку, решить капчу,
скопировать напечатанное.

- Объём работ: **~2 часа**. Зависимостей нет. Работает везде и всегда.
- Минуты ядра на это точно не хватит — константу придётся растить (см. §6).
- Это и есть «ручной режим» в формулировке Э1; ценность его не в удобстве, а в том, что
  он работает, когда не работает ничто другое.

## 6. Общее для всех вариантов: минуту нужно растить

`captchaManualWebViewTimeout = 60 * time.Second` — величина, унаследованная от Android,
где окно капчи всплывало само и мгновенно. У нас в эту минуту укладываются ещё и запуск
браузера или окна. Для консольного варианта её не хватает заведомо.

Правка вносится **только** правилом переноса ядра (тогда `scripts/vendor-core.ps1`, теперь
`scripts/vendorcore/rules.go`) — иначе не переживёт следующий
перенос ядра. Предлагается 180 секунд: три минуты человеку хватает, а цена ошибки — это
задержка одного воркера, пока остальные продолжают работать.

Побочных эффектов немного: `globalCaptchaLockout` (60 с) отсчитывается после отказа, а не
до, и на него величина не влияет; наш диспетчер и так не зовёт человека на короткие окна.

## 7. Сравнение и рекомендация

| | Консоль | WebView2 (3) | Браузер/CDP (2) |
|---|---|---|---|
| Платформы | все | Windows | все |
| Что нужно установленным | ничего | WebView2 Runtime | Chromium |
| Действий от пользователя | 5, одно из них — F12 | 1: решить капчу | 1: решить капчу |
| Новых зависимостей | 0 | 2 (MIT, без cgo) | 1 или свой код |
| Видно ли VK вмешательство | нет | подменён `fetch` | нет |
| Объём работ | ~2 ч | 0.5–1 д | 1.5–2 д |
| Риск | низкий | низкий | средний |

**Рекомендация — делать не «или», а «и», в три приёма:**

1. **Сейчас, в E2: консольный решатель.** Это буквально то, что записано в Э1, он работает
   всегда и служит запасным дном для двух других. Вместе с ним — правка таймаута до 180 с.
   `qwdtt-cli connect` после этого закрывается целиком, и критический путь `E2 → G2 → H2`
   разблокирован ценой пары часов.
2. **Следом, всё ещё в Э1: WebView2.** Соотношение «полдня работы — и на целевой платформе
   пользователю остаётся один шаг вместо пяти» лучшее из трёх. Перенос из Э2 в Э1 оправдан
   именно этим: без него Э1 на Windows формально готов, но пользоваться им неприятно.
   Чистая деградация на отсутствующий Runtime уже предусмотрена §08 архитектуры.
3. **Вариант 2 — к Э4, где он единственный разумный.** На Linux и macOS WebView2 нет, и
   CDP там будет не «ещё одним способом», а единственным приличным. Делать его сейчас,
   когда datapath для этих систем всё равно появится только в Э4, значит платить два дня
   за то, чем пока негде пользоваться.

Порядок этот ещё и снижает риск: каждый следующий приём опирается на работающий предыдущий,
а перехватчик JS и разбор `success_token` пишутся один раз и переиспользуются всеми тремя.

### Что для этого нужно от `solver.go`

Ничего, кроме двух общих кусков, которые стоит завести сразу в E2 и не переписывать потом:

- `interceptorJS` — константа с перехватчиком (одна на WebView2 и на консольный
  однострочник; CDP её не использует, но пусть лежит рядом);
- `successTokenFrom(body []byte) (string, error)` — разбор ответа `captchaNotRobot.check`
  с различением трёх исходов: токен, слайдер, ошибка VK. Нужен и CDP, и тестам.

## 8. Принятые решения

1. **Порядок из §7 принят:** консоль сейчас, WebView2 следом в Э1, CDP к Э4. Консоль и
   WebView2 сделаны; CDP в Э4 не попал, записан задачей в `architecture.md`, §11 («Капча в
   браузере под управлением (CDP) на Linux»), и сделан там — только на Linux.
2. **Таймаут растим до 180 с** — правилом переноса ядра (теперь — `scripts/vendorcore/rules.go`).
3. **Транспорт для CDP** выбирается тогда, когда до CDP дойдёт дело: вопрос
   не блокирует ни консольный решатель, ни WebView2. Выбрана труба (§4).

### Что из этого уже сделано (задача E2, первый приём)

- `internal/captcha/token.go` — `interceptorJS`, `successTokenFrom` и `consoleSnippet`.
  Общие для всех трёх решателей, писать их второй раз не придётся.
- `internal/captcha/manual.go` — консольный решатель.
- `internal/captcha/open.go` — `OpenInBrowser`, передаётся решателю полем.
- Правило переноса на 180 секунд.

### Второй приём — сделан в задаче E3

`internal/captcha/webview2_windows.go`, заглушка `webview2_other.go`, выбор решателя —
`captchaSolver` в `internal/cli/connect.go`. Поправки к эскизу §3 — во врезке там же.
Ниже — как задача ставилась.

#### Как ставилась

Окно WebView2 по §3: `internal/captcha/webview2_windows.go` плюс заглушка для остальных
систем. Зависимости — `github.com/jchv/go-webview2` и `github.com/jchv/go-winloader`,
обе MIT и без cgo. Проверка среды — `webviewloader.GetInstalledVersion()`; её отказ
означает откат на консольный решатель, который к тому времени уже работает. Перехватчик
берётся готовым из `token.go`: подставить в `%s` имя функции, заведённой через `Bind`.

Подводные камни перечислены в §3 — ручка окна наружу для `Terminate()`, временный профиль,
который не удаляется сразу, и недоступный через верхний интерфейс `PutUserAgent`.
